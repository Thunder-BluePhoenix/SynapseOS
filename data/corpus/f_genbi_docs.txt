# F-GenBI — Generative Business Intelligence + Excel View for ERPNext

**F-GenBI** is a standalone Frappe app that bundles two deeply integrated systems:

1. **GenBI** — Ask business questions in plain English; get instant answers as charts, tables, and number cards.
2. **Excel View** — A spreadsheet-grade list view for any Frappe DocType, with inline editing, child table popups, conditional formatting, Flash Fill, formula support, pivot tables, and more.

Neither system requires the upstream `excel_view` app to be installed. F-GenBI ships everything self-contained with its own asset bundles and API layer.

## What's Inside

### Excel View

A full spreadsheet experience inside Frappe — powered by [Handsontable](https://handsontable.com/).

| **Column reorder** | Drag columns; order persists per user |

### GenBI

Natural language → SQL → visualization, with a conversational chat interface.

| Capability | Detail |
|---|---|
| **NL → SQL** | Converts plain English to safe, read-only SQL |
| **Multi-provider LLM** | Ollama (local), OpenAI, Anthropic, Gemini, any OpenAI-compatible endpoint |
| **No-LLM local engine** | `SQLTemplateEngine` handles common patterns offline (no API key needed) |
| **Streaming responses** | Live SSE streaming via Socket.IO; falls back to standard call |
| **Conversation memory** | Last 10 exchanges kept per session; sessions persisted to DB |
| **Intent classification** | Query intent detected to inject LLM hints and route to specialist handlers |
| **Entity resolution** | Alias → DocType mapping with Redis tier-1 cache, fed by feedback loop |
| **Explain Mode** | Explains terms, anomalies, normal ranges, and relationships |
| **Predictive analytics** | Linear regression trend + N-period projection (`FORECAST` intent) |
| **Anomaly detection** | Daily job; 25% deviation from 30-day avg fires Frappe Notification |
| **Multi-company routing** | Auto-injects company filter per user's allowed companies |
| **Query result caching** | Redis cache with 5-min TTL, user-scoped |
| **SELECT * ranking** | Scores fields by `in_list_view×40 + bold×20 + reqd×10` |
| **Child table bracket notation** | `items[2].rate` in field traversal |
| **Training loop** | 👍 feedback promotes examples to few-shot prompts for future queries |
| **Fine-tuning export** | Export training dataset as Alpaca / OpenAI / raw JSONL |
| **NLP preloading** | sentence-transformers + spaCy loaded at worker startup |

## 1. No-LLM Local Engine

**The insight:** The `genbi/` modules (`intent_classifier`, `query_parser`, `entity_resolver`, `explainer`, `data_insights`) are fully built but completely disconnected from the main `query_engine.py`. Together, they can power a complete offline SQL generation pipeline — no LLM API key required.

### How It Works

```
User Question
  ↓ intent_classifier.py   →  INTENT (LIST / AGGREGATE / TREND / LOOKUP / EXPLAIN / COMPARE)
  ↓ entity_resolver.py     →  [{doctype: "Sales Invoice", confidence: 0.92}, ...]
  ↓ query_parser.py        →  {entities, fields, filters, group_by, aggregates, confidence}
  ↓ schema_builder.py      →  field names + table names for resolved entities
  ↓ SQLTemplateEngine      →  fills template → valid, safe SQL
  ↓ Execute + Visualize    →  same downstream pipeline as LLM path
```

### SQL Templates by Intent

| Intent | SQL Template |
|--------|-------------|
| LIST | `SELECT {fields} FROM \`tab{DocType}\` WHERE {filters} ORDER BY creation DESC LIMIT 50` |
| AGGREGATE | `SELECT {group_field}, {fn}({agg_field}) as total FROM \`tab{DocType}\` WHERE {filters} GROUP BY {group_field} ORDER BY total DESC` |
| TREND | `SELECT DATE_FORMAT(posting_date,'%Y-%m') month, SUM(grand_total) total FROM \`tab{DocType}\` GROUP BY month ORDER BY month` |
| LOOKUP | `SELECT {fields} FROM \`tab{DocType}\` WHERE name LIKE %s OR {label_field} LIKE %s LIMIT 20` |
| JOIN | `SELECT p.name, {child_fields} FROM \`tab{Parent}\` p JOIN \`tab{Child}\` c ON c.parent=p.name WHERE {filters}` |
| EXPLAIN | → trigger `explainer.py` directly, no SQL needed |
| COMPARE | `SELECT {group_field}, {fn}({agg_field}) FROM \`tab{DocType}\` WHERE {date_field} BETWEEN %s AND %s GROUP BY {group_field}` |

### Why This Is Powerful

- **Zero API cost** — no per-token charges
- **Zero latency** — sub-100ms responses vs 2-8s LLM round trips
- **Air-gapped deployment** — works on factory floors, hospitals, government (no internet needed)
- **Privacy** — data never leaves the server
- **Handles ~70% of daily queries** — top N, totals by category, trends, lookups, record details
- **Graceful degradation** — "I can handle simple queries offline. For complex analysis, please configure an LLM."

### GenBI Settings Change

Add `"None (Local NLP Engine)"` as the **first and default** option in the `llm_provider` dropdown. When selected, the full `genbi/` pipeline activates instead of any LLM call.

## 2. Wiring Unused NLP Modules

### A. Intent Classifier → LLM Context Injection

**Current:** LLM receives question + schema cold.
**Improved:** Pre-classify intent → inject as a structured hint into the LLM system prompt.

```python
intent_result = classify_intent(question)
# → {"intent": "ANALYZE_DATA", "confidence": 0.87, "sub_intent": "trend"}

# Appended to system prompt:
# "User intent detected: ANALYZE_DATA (trend analysis).
#  Prefer GROUP BY month, SUM aggregates, and line/bar chart types."
```

**Intent → Behaviour Map:**

| Intent | LLM Behaviour Change |
|--------|---------------------|
| FIND_PATH | Include `explainer.py` relationship context in prompt |
| ANALYZE_DATA | Emphasise GROUP BY, SUM, COUNT; prefer chart |
| EXPLAIN | Skip SQL entirely; call `explainer.py`; return explanation |
| REFINE | Force use of previous conversation SQL as starting point |
| BUILD_CANVAS | Suggest Excel View / Canvas Session |
| SUGGEST | Return quick insights / suggestions list |

### B. Entity Resolver → Accurate Schema Lookup

**Current:** `schema_builder` uses simple keyword regex on the raw question — brittle.
**Improved:** Resolve entities first, pass resolved DocType list to schema builder.

```python
entities = entity_resolver.resolve(question)
# → [{"doctype": "Sales Invoice", "confidence": 0.94}, {"doctype": "Customer", "confidence": 0.81}]

schema = schema_builder.get_schema_for_doctypes([e["doctype"] for e in entities])
```

Eliminates wrong-schema bugs (e.g., "material request" accidentally matching "Sales" keywords).
The resolver's 5-stage pipeline (Redis cache → aliases → fuzzy → semantic) ensures high accuracy.

### C. Query Parser → Structured LLM Hints

spaCy extracts `{filters, group_by, aggregates}` from the sentence structure. Even if imperfect, this constrains the LLM and reduces hallucination:

```python
parse = query_parser.parse(question)
# → {filters: [{field: "status", op: "=", value: "Submitted"}], group_by: "customer_name"}

# Injected into LLM prompt:
# "Structural analysis detected: filter on status='Submitted', group by customer_name.
#  Validate your SQL includes these constraints."
```

### D. Data Insights → Pre-Query Warnings

Run `data_insights.analyze()` before generating any SQL. Give the user a heads-up, and give the LLM cardinality context:

```python
insights = data_insights.analyze(resolved_entities)
# → {"row_counts": {"Sales Invoice": 85000}, "warnings": ["1:N join may produce 850K rows"]}

# Show to user: "Note: Sales Invoice has 85,000 records. Add filters to narrow results."
# Add to LLM prompt: "Table has 85K rows. Ensure LIMIT and WHERE clause are present."
```

### E. Explainer → Conversational Relationship Answers

When intent is EXPLAIN or FIND_PATH, bypass SQL entirely:

```python
if intent == "EXPLAIN":
    explanation = explainer.explain_path(entities[0], entities[1])
    return {"type": "chat", "message": explanation}
```

Returns a human-readable business context explanation ("Sales Order links to Customer via customer field, and to Sales Invoice through the billing process...").

## 3. Filling Structural Gaps

### Gap 1: Hard-Coded Child Table Map

**Current:** 8 hard-coded parent→child pairs in `query_engine.py`.
**Fix:** Discover dynamically from DocField metadata at startup.

```python
# Runs once at startup, cached in Redis:
child_map = {
    row.parent: row.options
    for row in frappe.db.get_all("DocField",
        filters={"fieldtype": "Table"},
        fields=["parent", "options"]
    )
}
# Covers ALL installed apps automatically — ERPNext, HRMS, Healthcare, etc.
```

### Gap 2: SELECT * Column Ranking

**Current:** Picks first 15 columns arbitrarily.
**Fix:** Rank by business relevance signals from DocField metadata.

```python
# Priority order:
# 1. in_list_view = 1  (fields shown in Frappe list view — most relevant)
# 2. bold = 1           (highlighted fields)
# 3. reqd = 1           (mandatory fields — business-critical)
# 4. fieldtype in [Currency, Float, Int, Date]  (numeric/date fields)
# 5. Everything else
```

### Gap 3: Conversation Not Persisted

**Current:** Redis only, 1-hour TTL — lost on restart.
**Fix:** Add `GenBI Chat Session` DocType.

```
GenBI Chat Session
├── name          (auto UUID)
├── user          (Link → User)
├── session_title (first question, truncated to 60 chars)
├── chat_history  (JSON)
├── created_at    (DateTime)
├── last_activity (DateTime)
└── is_pinned     (Check — user can pin important sessions)
```

Sync to Redis on write, load from DB on cache miss.

### Gap 4: No SQL Result Cache

**Current:** Every identical question re-runs the LLM + DB query.
**Fix:** Cache SQL results keyed by `hash(sql) + frappe.session.user`.

```python
cache_key = f"genbi_result_{md5(sql)}_{frappe.session.user}"
cached = frappe.cache().get_value(cache_key)
if cached:
    return cached
# ... execute query ...
frappe.cache().set_value(cache_key, result, expires_in_sec=300)  # 5 min TTL
```

### Gap 5: No Test Connection in Settings

**Current:** Users configure LLM settings and only find out they're wrong when a query fails.
**Fix:** Add a "Test Connection" button in GenBI Settings that pings the provider and returns latency.

### Gap 6: Model List Not Dynamic

**Current:** User must manually type model names (typo-prone).
**Fix:** For Ollama and OpenAI, fetch available models via their APIs and populate a dropdown.

### D. Anomaly Detection + Proactive Alerts

Background daily job compares KPIs to rolling 4-week average:

```python
# Pseudocode:
for kpi in ["grand_total", "outstanding_amount", "qty"]:
    this_week = run_query(f"SELECT SUM({kpi}) FROM `tab{doctype}` WHERE ...")
    avg_4wk   = run_query(f"SELECT AVG(weekly_total) FROM ...")
    if deviation(this_week, avg_4wk) > 2_sigma:
        frappe.publish_realtime("genbi_alert", {
            "message": f"Revenue dropped 38% vs 4-week average",
            "severity": "warning"
        })
```

Uses `data_insights.py` cardinality analysis as the foundation.

## 5. Performance Improvements

| Area | Current State | Improvement |
|------|--------------|-------------|
| Schema lookup | Keyword regex on every request | Cache by `hash(keywords)`, 5-min TTL in Redis |
| NLP model loading | Lazy on first request (~3s cold start) | Preload at app init in background thread |

### Streaming (Highest Perceived Performance Gain)

    # 3. Stream LLM tokens as they arrive
    # 4. Execute SQL while streaming continues
    # 5. Send final data payload as last SSE event

```

## 1. The Core Idea

**One sentence:** Replace guessing with a trained neural model that understands ERPNext questions and builds SQL from structured understanding — without any internet, API key, or external LLM.

**The system has three tiers:**

```
Tier 1 — Zero setup:   Schema-Driven Compiler (no models, no training, works day 1)
Tier 2 — Trained:      Neural Slot Filler + T5-small (ONNX, auto-trains from usage)
Tier 3 — Turbo:        frappe_rpg Rust + f_lightning Go (optional installed apps)
```

Each tier is independent. Users get Tier 1 immediately. Tiers 2 and 3 are additive improvements.

---

## 2. Why the Local Engine Has a Ceiling

The existing `LocalNLPEngine` fails not because it lacks intelligence — it fails because `SQLTemplateEngine` can only build **6 rigid SQL shapes**.

Even if the NLP correctly understands the question, if it doesn't fit a template → unsupported.

```
Current 6 shapes only:
  LIST, LOOKUP, AGGREGATE, TREND, JOIN, COMPARE

Anything else → "I can't handle this offline"
```

Also: PatternEngine has 24 hardcoded regex patterns. Every new query pattern requires a developer to add a new regex. It doesn't scale.

**The Neural Engine fixes this with a schema-aware, self-extending approach.**

---

## 3. Design Decision — Standalone Engine

**The Neural Engine is a completely new, standalone engine.** `local_engine.py` is not touched.

```
GenBI Settings → LLM Provider dropdown:
  OpenAI                    ← cloud
  Anthropic                 ← cloud
  Google Gemini             ← cloud
  Ollama (Local LLM)        ← local LLM server
  None (Local NLP Engine)   ← existing, unchanged
  Neural (Local)            ← NEW — this engine
  Neural + RPG Boost        ← NEW — needs frappe_rpg installed
  Neural + Lightning        ← NEW — needs f_lightning installed
```

`query_engine.py` gets one new routing branch:

```python
elif settings.llm_provider in ("Neural (Local)", "Neural + RPG Boost", "Neural + Lightning"):
    from f_genbi.f_genbi.genbi.neural_engine import NeuralEngine

```

## 4. Full 5-Layer Architecture

```
User Question
      │
      ▼
NeuralEngine.process()
      │
      ├─ Layer 0: PatternEngine (regex, 24 patterns, ~40% of queries)
      │       └── hit → SQL ✅  (engine: "neural-pattern")
      │
      ├─ Layer 1: Schema-Driven Compiler (no models, pure rules + live meta)
      │       └── confidence ≥ 0.75 → SQL ✅  (engine: "neural-schema")
      │               str | None:
    return _pattern_engine.match(question, company)
```

Fast (~0ms), 100% accurate for the 24 known patterns. Zero ML overhead. Runs first.

**Key insight:** Adding new patterns to the Neural Engine costs nothing — just add to `PatternEngine`. PatternEngine speed is O(1) regardless of how many patterns exist (all compiled into one regex).

## 6. Layer 1 — Schema-Driven Compiler (No Models)

**The most important layer.** Works from Day 1 with zero models, zero training, zero downloads. Accuracy: ~78%.

### How It Works

### Field Resolution (no ML — pure string matching)

```python
def resolve_field_mention(word: str, doctype: str) -> str | None:
    word_lower = word.lower().rstrip("s")  # plurals: "customers" → "customer"
    meta = frappe.get_meta(doctype)
    for field in meta.fields:
        label = (field.label or field.fieldname).lower()
        if word_lower in label or word_lower in field.fieldname.lower():
            return field.fieldname
    return None
```

### NeuralSQLBuilder

Schema-aware SQL construction — every field name verified against `frappe.get_meta()`:

- Knows which DocTypes are submittable → injects `docstatus=1`

- Builds JOIN paths via Relationship Graph (discovered from DocField meta)
- Confidence drops when field can't be verified → falls to Layer 2

## 7. Layer 2 — Neural Slot Filler (DistilBERT-tiny ONNX)

### What It Is

A **DistilBERT-tiny** model fine-tuned specifically on ERPNext business questions. Multi-label classifier — one head per slot.

### Slots

| Slot | Values |
|---|---|
| `intent` | LIST, AGGREGATE, TREND, COMPARE, LOOKUP, JOIN, COUNT, TOP_N |
| `entity` | Any Frappe DocType |
| `group_by` | customer, supplier, item, month, year, department, territory, status, warehouse |
| `agg_type` | SUM, COUNT, AVG, MAX, MIN |
| `value_keyword` | grand_total, qty, outstanding_amount, paid_amount, amount |
| `date_ref` | today, this_month, last_month, this_year, last_year, last_7_days, last_30_days |
| `limit_n` | integer |
| `filter_status` | Submitted, Draft, Cancelled, Open, Active |
| `confidence` | float 0.0–1.0 |

### Schema Injection (Key Accuracy Boost)

```

### Size

- `prajjwal1/bert-tiny` → INT8 ONNX → **~16MB**
- Inference: **~20ms on CPU**

## 11. Power-Up Ideas

### A — Self-Learning Loop
Every 👍 → training example → weekly micro fine-tune → ONNX hot-swap. Improves automatically.

### B — Conversation Memory Injection
Last 3 Q+SQL turns injected into slot filler input. "filter to this month" inherits previous DocType/entity.

### C — Vector Store Memory (FAISS)
Pre-embed all training examples. New question → cosine similarity → if top-1 ≥ 0.92, adapt that SQL directly (EntityResolver swaps entity names). Zero training needed, works immediately.

### D — Query Decomposer (AND/OR/BUT NOT)
Detect logical connectors, split into sub-questions, run each through slot filler independently, merge with Python set logic. No SQL subqueries.

```
"Customers in Delhi who have open orders but no outstanding invoices"
→ Sub A: customers in Delhi with open Sales Orders
→ Sub B: customers with outstanding Sales Invoices
→ Python: A - B (set difference)
```

### E — Schema Auto-Discovery (Custom DocTypes)
Unknown DocType field → embed the term → cosine similarity against all field labels in `frappe.get_meta()` → find best match. Uses `all-MiniLM-L6-v2` already loaded. No retraining.

## 22. Streaming Support for Neural Engine

### The Problem

`stream_question()` currently only emits realtime `frappe.publish_realtime` events on the LLM path. If a user switches to the Neural Engine, `stream_question()` routes to the neural path — but no events are emitted. The chat UI shows a dead spinner until the response arrives all at once.

This is inconsistent UX and breaks the progressive loading experience built in Phase 2.

### The Fix

The Neural Engine knows each stage deterministically — unlike an LLM it doesn't need to "think". It should emit exactly the same event shape as the LLM path:

```python
# neural_engine.py — emit at each stage
def process(self, question, chat_history=None, stream_id=None):
    def _emit(stage, data=None):
        if stream_id:
            frappe.publish_realtime(
                f"genbi_stream_{stream_id}",
                {"event": stage, **(data or {})},
                user=frappe.session.user,
                after_commit=False,
            )

    # Layer 0: PatternEngine
    _emit("schema_ready", {"doctypes": [], "engine": "neural-pattern"})
    result = _try_pattern_engine(question)
    if result:
        _emit("sql_ready", {"sql": result})
        rows, _ = _execute_query(result, max_rows)
        _emit("data_ready", {"result_count": len(rows)})
        _emit("done", full_result)
        return full_result

    # Layer 1: Schema Compiler
    _emit("schema_ready", {"doctypes": [entity], "engine": "neural-schema"})
    slots = schema_parser.parse(question)
    sql, conf = sql_builder.build(slots)
    if sql:
        _emit("sql_ready", {"sql": sql, "confidence": conf})
        ...

    # etc. for each layer
```

### Why It Matters

- Consistent UX regardless of engine selected — users don't notice switching
- Progressive status updates: "Understanding schema..." → "Building SQL..." → "Executing..."
- For the Neural Engine the stages complete in milliseconds, but the frontend still benefits (shows which layer answered)

### Stage Labels per Layer

| Layer | `schema_ready` message | `sql_ready` note |
|---|---|---|
| PatternEngine | `"Matched pattern"` | Instant |
| Schema Compiler | `"Schema vocabulary matched"` | Built in Python |
| Slot Filler | `"Neural model processing..."` | ~20ms ONNX |
| T5 Seq2Seq | `"Deep inference..."` | ~500ms ONNX |
| Clarification | — | Dialog shown instead |

**Implementation scope:** ~30 lines added to `neural_engine.py`. No new files.

## 25. SQL Dry-Run Validator

### The Problem

`NeuralSQLBuilder` assembles SQL from slots using `frappe.get_meta()`. But there are edge cases where the generated SQL is syntactically valid but semantically wrong for MariaDB — e.g.:

- A field exists in meta but is a child table field (not queryable on the parent)
- A JOIN path is incorrect (wrong alias)
- A date function is used on a non-date column

These cause a MariaDB error at execution time, which shows the user a raw error message.

### The Fix: EXPLAIN Before Execute

After `NeuralSQLBuilder.build()` produces SQL, run `EXPLAIN` before the real execute:

```python
def _dry_run_validate(sql: str) -> tuple[bool, str | None]:
    """
    Run EXPLAIN on the SQL to catch MariaDB-level errors before execution.
    Returns (is_valid, error_message_or_None).

    Never raises — always returns a tuple.
    Cost: ~1ms (EXPLAIN does not execute the query).
    """
    try:
        frappe.db.sql(f"EXPLAIN {sql}")
        return True, None
    except Exception as e:
        return False, str(e)
```

**Used in `neural_engine.py`:**

```python
sql, confidence = sql_builder.build(slots)
if sql:
    valid, err = _dry_run_validate(sql)
    if valid:
        return _execute_and_return(sql, engine="neural")
    else:
        # Don't show raw error — route to next layer with context
        frappe.logger().warning(f"NeuralSQLBuilder dry-run failed: {err}")
        confidence = 0.0   # force fallthrough to T5 or clarification
```

### Benefits

- Users never see a raw `OperationalError: Unknown column 'xxx'`
- Neural Engine fails gracefully — routes to next layer silently
- The error is logged for developer inspection
- ~1ms overhead — EXPLAIN is free in MariaDB (no rows read)

### Also: Schema Pre-Check (Before EXPLAIN)

A lighter check before even calling EXPLAIN — verify all table/field references
against `frappe.get_meta()` before generating SQL:

```python
def _verify_fields(slots: SlotResult) -> list[str]:
    """
    Returns list of field names that could not be verified against live meta.
    Empty list = all fields verified.
    """
    unverified = []
    meta = frappe.get_meta(slots.entity)
    valid_fields = {f.fieldname for f in meta.fields}
    for field in [slots.group_by, slots.value_keyword]:
        if field and field not in valid_fields:
            unverified.append(field)
    return unverified
```

If `_verify_fields()` returns anything → confidence drops by 0.2 before building SQL.

## 26. Template-Based Explanation Generator

### The Problem

The `_summarize_results()` function in `query_engine.py` makes a **second LLM call** to generate a friendly conversational explanation of the query results. With the Neural Engine (no LLM), this call can't be made. The response would have empty or null `explanation`.

### The Fix: Deterministic Template Engine

A `NeuralExplainer` class that generates natural-sounding summaries from slots + data without any LLM:

```python
class NeuralExplainer:
    """
    Generates conversational result summaries from slots + data rows.
    No LLM. Deterministic. Supports multiple locales.
    """

    def summarise(self, slots: SlotResult, rows: list[dict], question: str) -> str:
        if not rows:
            return self._no_results(slots)

        match slots.intent:
            case "TOP_N":    return self._explain_top_n(slots, rows)
            case "TREND":    return self._explain_trend(slots, rows)
            case "AGGREGATE":return self._explain_aggregate(slots, rows)
            case "LOOKUP":   return self._explain_lookup(slots, rows)
            case "COUNT":    return self._explain_count(slots, rows)
            case _:          return self._explain_generic(slots, rows)

    def _explain_top_n(self, slots, rows) -> str:
        top = rows[0]
        val_field = slots.value_keyword or list(rows[0].keys())[-1]
        grp_field = slots.group_by or list(rows[0].keys())[0]
        top_name  = top.get(grp_field, "?")
        top_val   = _fmt_number(top.get(val_field, 0))
        period    = _period_label(slots.date_ref)
        return (
            f"Top {slots.limit_n or len(rows)} {slots.entity or 'records'} "
            f"by {val_field.replace('_', ' ')}{period}. "
            f"Highest: **{top_name}** with {top_val}."
        )

    def _explain_trend(self, slots, rows) -> str:
        vals = [float(r.get(slots.value_keyword or 'value', 0) or 0) for r in rows]
        direction = "↑ increasing" if vals[-1] > vals[0] else "↓ decreasing"
        pct = abs((vals[-1] - vals[0]) / vals[0] * 100) if vals[0] else 0
        return (
            f"{slots.entity or 'Data'} trend over {len(rows)} periods is "
            f"**{direction}** ({pct:.1f}% change from first to last period)."
        )

    def _explain_aggregate(self, slots, rows) -> str:
        row   = rows[0]
        keys  = list(row.keys())
        if len(keys) >= 2:
            # Grouped aggregate: N groups
            return (
                f"{slots.entity or 'Data'} grouped by {slots.group_by or keys[0]}: "
                f"{len(rows)} groups found."
            )
        else:
            # Single value
            val = _fmt_number(list(row.values())[0])
            return f"Total {keys[0].replace('_', ' ')}: **{val}**."

    def _explain_count(self, slots, rows) -> str:
        count = list(rows[0].values())[0] if rows else 0
        period = _period_label(slots.date_ref)
        return f"Found **{count:,}** {slots.entity or 'records'}{period}."

    def _no_results(self, slots) -> str:
        period = _period_label(slots.date_ref)
        return f"No {slots.entity or 'records'} found{period}."


def _fmt_number(val) -> str:
    """Format a number nicely: 1500000 → '15.0L' or '1.5M' based on locale."""
    try:
        n = float(val)
        if n >= 1e9:  return f"{n/1e9:.2f}B"
        if n >= 1e7:  return f"{n/1e7:.2f}Cr"   # Indian
        if n >= 1e5:  return f"{n/1e5:.2f}L"    # Indian
        if n >= 1e6:  return f"{n/1e6:.2f}M"
        if n >= 1e3:  return f"{n/1e3:.1f}K"
        return str(round(n, 2))
    except (TypeError, ValueError):
        return str(val)


def _period_label(date_ref: str) -> str:
    labels = {
        "today":        " today",
        "this_month":   " this month",
        "last_month":   " last month",
        "this_year":    " this year",
        "last_year":    " last year",
        "last_7_days":  " in the last 7 days",
        "last_30_days": " in the last 30 days",
    }
    return labels.get(date_ref or "", "")
```

|---|---|---|

### 10.1 `enforce_permissions` checkbox + `_inject_permission_filters()`

**The problem:** `NeuralSQLBuilder` builds SQL from DocType names and field names without
checking whether the current user is allowed to see that data. A non-manager asking
"show all salary slips" would get every employee's salary.

**Solution — opt-in checkbox in GenBI Settings (Security section):**

```
Security
────────────────────────────────────────
☐  Enforce Frappe Permissions           ← default OFF
   When enabled, generated SQL is filtered by the current user's
   Frappe row-level permissions and User Permissions.
   When disabled, all rows are returned regardless of access rules.
```

Default is **OFF** so existing installations are not broken on upgrade.
System Managers enable it when they want user-scoped data access.

**Backend — `_inject_permission_filters()` called only when checkbox is ON:**

```python
# query_engine.py — shared helper used by all execution paths
def _inject_permission_filters(sql: str, doctype: str, user: str) -> str:
    """
    Called only when GenBI Settings → enforce_permissions == 1.
    Appends Frappe row-level permission conditions to generated SQL.
    """
    settings = frappe.get_single("GenBI Settings")
    if not settings.enforce_permissions:
        return sql   # bypass — checkbox is OFF

    # 1. DocType-level read gate
    if not frappe.has_permission(doctype, ptype="read", user=user, raise_exception=False):
        frappe.throw(
            f"You do not have read permission on {doctype}.",
            frappe.PermissionError
        )

    # 2. User Permission filters (company scope, territory scope, etc.)
    user_perms = frappe.get_user_permissions(user)
    extra_conditions = _build_user_permission_conditions(doctype, user_perms)

    if not extra_conditions:
        return sql

    # Inject into existing WHERE or add new WHERE before GROUP BY / ORDER BY
    sql_upper = sql.upper()
    if " WHERE " in sql_upper:
        idx = sql_upper.index(" WHERE ") + 7
        return sql[:idx] + extra_conditions + " AND " + sql[idx:]
    elif " GROUP BY " in sql_upper:
        idx = sql_upper.index(" GROUP BY ")
        return sql[:idx] + " WHERE " + extra_conditions + sql[idx:]
    else:
        return sql + " WHERE " + extra_conditions
```

**Wired in:** `neural_engine._build_done()` before execution for all 5 layers.
Also in `query_engine._execute_query()` as a second safety net.

**Acceptance criteria:**
- [ ] `enforce_permissions = 0` (default) → all rows returned, no WHERE injected (no regression)
- [ ] `enforce_permissions = 1` + user without read on `Salary Slip` → PermissionError
- [ ] `enforce_permissions = 1` + company-scoped User Permission → `company = 'X'` injected
- [ ] Admin user with enforcement ON → no extra conditions (admin has all permissions)
- [ ] Toggle visible in GenBI Settings → Security section
- [ ] No code change needed to toggle — pure settings-driven

### 10.3 SQL-level safety hardening

Centralise and strengthen the existing SQL safety checks into one function:

```python
# query_engine.py (or a new security.py)
_BLOCKED_PATTERNS = [
    r'\bINSERT\b', r'\bUPDATE\b', r'\bDELETE\b', r'\bDROP\b',
    r'\bCREATE\b', r'\bALTER\b', r'\bTRUNCATE\b', r'\bEXEC\b',
    r'INFORMATION_SCHEMA', r'`mysql`\.', r'`sys`\.',
    r'INTO\s+OUTFILE', r'INTO\s+DUMPFILE',
    r'LOAD_FILE\s*\(',
    r';\s*SELECT',      # multi-statement
    r'SLEEP\s*\(',      # time-based blind injection
    r'BENCHMARK\s*\(',
]

def validate_sql_safety(sql: str) -> None:
    """Raises frappe.ValidationError if sql contains dangerous patterns."""
    sql_upper = sql.upper()
    if not sql_upper.strip().startswith("SELECT"):
        frappe.throw("Only SELECT queries are allowed.", frappe.ValidationError)
    for pat in _BLOCKED_PATTERNS:
        if re.search(pat, sql_upper):
            frappe.throw(f"Query blocked: disallowed pattern detected.", frappe.ValidationError)
```

**Acceptance criteria:**
- [ ] `INSERT INTO ...` → blocked
- [ ] `SELECT * FROM information_schema.tables` → blocked
- [ ] `SELECT 1; DROP TABLE ...` → blocked (multi-statement)
- [ ] `SELECT SLEEP(5)` → blocked
- [ ] Valid SELECT with subqueries → allowed

@frappe.whitelist()
def create_shared_result(sql, question, rows_json, chart_type, columns) -> dict:
    token = str(uuid.uuid4()).replace("-", "")[:16]
    expires = frappe.utils.add_days(frappe.utils.now(), 7)

def get_shared_result(token: str) -> dict:

### 2.1 LLM Response Streaming (SSE)

**New endpoint:** `process_question_stream()` in `query_engine.py`

**Architecture:**

```
Browser                          Frappe Worker
   |                                  |
   |-- POST /process_question_stream →|
   |                                  |-- Schema fetch (fast)
   |← token: "Based on..."           |-- LLM stream opens
   |← token: " your sales..."        |-- tokens forwarded as SSE
   |← token: " data, I found..."     |
   |                                  |-- SQL executes in parallel thread
   |← event: {type: "sql", sql: ...} |
   |← event: {type: "result", ...}   |-- Final data sent
   |← event: {type: "done"}          |
```

**Implementation:**
```python
@frappe.whitelist()
def process_question_stream(question, chat_history="[]"):
    frappe.response["content_type"] = "text/event-stream"
    frappe.response["headers"] = {
        "Cache-Control": "no-cache",
        "X-Accel-Buffering": "no"  # disable nginx buffering
    }
    def generate():
        for chunk in _stream_llm(question, schema, settings):
            yield f"data: {json.dumps({'type': 'token', 'text': chunk})}\n\n"
        # ... execute SQL, yield result ...
        yield f"data: {json.dumps({'type': 'done'})}\n\n"
    return generate()
```

**Frontend changes:**
- Replace `frappe.call()` with `EventSource` or `fetch()` with streaming reader
- Render tokens into the chat bubble as they arrive
- Show animated cursor while streaming
- SQL and chart appear after streaming completes

**Acceptance criteria:**
- [ ] First token appears within 500ms of submit
- [ ] Streaming works with Ollama, OpenAI, Anthropic, Gemini
- [ ] Fallback to non-streaming if SSE not supported
- [ ] Error mid-stream handled gracefully

### 4.1 Predictive Analytics

**New intent:** `FORECAST` in `intent_classifier.py`

**Trigger phrases:** "predict", "forecast", "next month", "projected", "expected", "will be"

**Backend:** New `f_genbi/f_genbi/genbi/forecaster.py`

```python
from sklearn.linear_model import LinearRegression
import numpy as np

class Forecaster:
    def forecast(self, question: str, doctype: str, value_field: str,
                 date_field: str, periods: int = 3) -> dict:
        """
        1. Fetch last 12 months of data
        2. Fit linear regression on time-indexed values
        3. Predict next N months
        4. Return actuals + forecast + confidence interval
        """
        historical = self._fetch_monthly_data(doctype, value_field, date_field)
        X = np.array(range(len(historical))).reshape(-1, 1)
        y = np.array([row["total"] for row in historical])

        model = LinearRegression().fit(X, y)
        future_X = np.array(range(len(historical), len(historical) + periods)).reshape(-1, 1)
        predictions = model.predict(future_X)

        return {
            "actuals": historical,
            "forecast": [

### 5.12 Template-Based Explanation Generator

**New file:** `f_genbi/f_genbi/genbi/neural_explainer.py`

Replaces LLM-generated explanations for Neural Engine results with deterministic, intent-specific templates. Zero API cost. Works air-gapped.

```python
class NeuralExplainer:
    """
    Generates human-readable explanations from SlotResult + row data.
    All methods are deterministic — no LLM, no randomness.
    """

    def explain(self, slots: SlotResult, rows: list[dict], sql: str) -> str:
        """Dispatch to the appropriate _explain_* method based on slots.intent."""
        dispatch = {
            "TOP_N":      self._explain_top_n,
            "AGGREGATE":  self._explain_aggregate,
            "TREND":      self._explain_trend,
            "LIST":       self._explain_list,
            "COUNT":      self._explain_count,
            "COMPARE":    self._explain_compare,
            "LOOKUP":     self._explain_lookup,
        }
        fn = dispatch.get(slots.intent, self._explain_generic)
        return fn(slots, rows)

    def _explain_top_n(self, slots, rows) -> str:
        # "Top 10 customers by revenue this month.
        #  #1 Acme Corp — ₹12,45,000 | #2 Globex — ₹9,80,000 | ..."
        ...

    def _explain_aggregate(self, slots, rows) -> str:
        # "Total grand total of Sales Invoices this month: ₹1,23,45,678"
        ...

    def _explain_trend(self, slots, rows) -> str:
        # "Monthly revenue for the last 6 months.
        #  Trend: ↑ increasing (+18% vs 6 months ago)"
        ...

    def _explain_count(self, slots, rows) -> str:
        # "Found 47 Sales Invoices matching your filters."
        ...

    def _explain_list(self, slots, rows) -> str:
        # "Showing 20 of 134 Sales Invoices (submitted, this month)."
        ...

    def _explain_compare(self, slots, rows) -> str:
        # "Comparison: this month ₹X vs last month ₹Y (↑ +12%)"
        ...

    def _explain_lookup(self, slots, rows) -> str:
        # "Found: Acme Corp Pvt Ltd (Customer) — GSTIN: 27AABCU9603R1ZX"
        ...

    def _explain_generic(self, slots, rows) -> str:
        # "Query returned N rows from {entity}."
        ...

    def _fmt_number(self, value: float, currency: str = "INR") -> str:
        """
        Format a float as a locale-aware string.
        Uses universal rules — no locale library dependency.
        Examples:
          INR: 1234567 → "₹12,34,567"   (South Asian grouping)
          USD: 1234567 → "$1,234,567"    (Western grouping)
          generic: 50000 → "50,000"
        """
        ...

    def _period_label(self, period_str: str) -> str:
        """
        Converts DB-format period strings to readable labels.
        "2025-04" → "April 2025"
        "2025-W14" → "Week 14, 2025"
        "2025" → "2025"
        """
        ...
```

# Phase 6 — Rust Core (`f_genbi_rs`)

> **Goal:** Build f_genbi's own PyO3 Rust module for 100x faster schema scanning,
> pattern matching, slot extraction, and SQL assembly.
> Self-contained — does not require frappe_rpg.

**Theme:** "Python stays readable; Rust handles the hot path."
**Estimated scope:** ~2–3 weeks (Rust build + Python bridge + verification)
**Prerequisite:** Phase 5 complete. maturin installed (`pip install maturin`).

---

## Architecture

```
Python NeuralEngine (hot path query)
        │
        ▼
rs_bridge.py
  try: from f_genbi_rs import scan_question, match_pattern, ...
  except ImportError: use pure Python (schema_vocabulary, local_engine)
        │
        ▼ (if Rust available)
f_genbi_rs.so  (compiled PyO3 extension)
  ├── schema_index.rs   Aho-Corasick vocabulary scan      (~0.2ms vs 15ms Python)
  ├── pattern_engine.rs RegexSet DFA, all 24 patterns     (~0.1ms vs 10ms Python)
  ├── slot_extractor.rs Rule-based slot extraction         (~0.5ms vs 40ms Python)
  └── sql_builder.rs    Zero-alloc SQL string assembly     (~0.1ms vs 3ms Python)
```

Rust path is **additive** — if the `.so` is not compiled, every caller falls through to the
existing pure-Python implementation unchanged. No user-visible behavior change.

---

## Conventions (mirrors frappe_rpg/rust/)

- `pyo3 = { version = "0.23", features = ["extension-module", "abi3-py310"] }`
- All Python-facing functions return `String` (JSON), never raw dicts
- Singletons via `OnceLock>`
- GIL-free reads via `DashMap` where applicable
- `rayon` for parallel schema vocabulary builds
- Follows `Bound` pattern from frappe_rpg's `lib.rs`

"""
rs_bridge.py — Thin bridge to f_genbi_rs Rust extension.

Tries to import compiled f_genbi_rs. If not available (e.g. first install

falls back to the pure-Python path.

    import f_genbi_rs as _rs
    _RUST_AVAILABLE = True
except ImportError:
    _rs = None
    _RUST_AVAILABLE = False


def is_rust_available() -> bool:
    return _RUST_AVAILABLE


def build_schema_index(vocab_json: str) -> None:
    if _rs:
        _rs.build_schema_index(vocab_json)


def scan_question(question: str) -> dict | None:
    if not _rs:
        return None
    import json
    return json.loads(_rs.scan_question(question))


def match_pattern(question: str, company: str = "") -> dict | None:
    if not _rs:
        return None

    return json.loads(_rs.match_pattern(question, company))


def extract_slots(question: str, schema_json: str = "{}") -> dict | None:
    if not _rs:
        return None
    import json
    return json.loads(_rs.extract_slots(question, schema_json))


def build_sql(slots_json: str, meta_json: str = "{}") -> dict | None:
    if not _rs:
        return None

    return json.loads(_rs.build_sql(slots_json, meta_json))

# Phase 9 — DuckDB Analytics + Neural Polish

> **Goal:** Add DuckDB in-process analytics for queries requiring window functions,
> PIVOT, running totals, and percentile rank — things MariaDB can't do natively.
> Also: ship a pre-trained base model with the app (Day 1 without any user training),
> and add multi-language explanation templates.

**Estimated scope:** ~1–2 weeks
**Prerequisite:** Phase 5 complete. `duckdb` pip-installable.

---

## Why DuckDB

MariaDB cannot do:
- `RANK() OVER (PARTITION BY ...)`
- `SUM(x) OVER (ORDER BY date)` (running totals)
- `PIVOT` / `UNPIVOT`
- `PERCENTILE_CONT(0.5) WITHIN GROUP`
- Arbitrary window functions

Users ask these questions: "running total of sales", "rank customers by revenue",
"show percentile distribution of invoice amounts". Currently these all fail or produce wrong SQL.

DuckDB (in-process, Python API) operates directly on the rows already fetched from MariaDB.
No separate server, no extra infrastructure.

---

## Tasks

### 9.1 `f_genbi/f_genbi/genbi/duckdb_engine.py`

```python
"""
duckdb_engine.py — In-process DuckDB analytics layer.

Takes rows already fetched from MariaDB and runs window/aggregate/pivot
SQL against them in-process. No MariaDB query involved.

DuckDB is optional — if not installed, this module returns None and
the caller falls back to the MariaDB result unchanged.
"""

import frappe

try:
    import duckdb as _duckdb
    _DUCKDB_AVAILABLE = True
except ImportError:
    _duckdb = None
    _DUCKDB_AVAILABLE = False


def is_available() -> bool:
    return _DUCKDB_AVAILABLE


def run_window_query(rows: list[dict], duckdb_sql: str) -> list[dict] | None:
    """
    Execute `duckdb_sql` against `rows` (treated as an in-memory table named `t`).
    Returns result rows or None if DuckDB unavailable or query fails.

    The caller is responsible for providing valid DuckDB SQL with table alias `t`.
    """
    if not _DUCKDB_AVAILABLE or not rows:
        return None
    try:
        import pandas as pd
        df = pd.DataFrame(rows)
        con = _duckdb.connect()
        con.register("t", df)
        result = con.execute(duckdb_sql).fetchdf()
        return result.to_dict(orient="records")
    except Exception as e:
        frappe.logger().debug(f"DuckDB query failed: {e}")
        return None


def build_window_sql(intent: str, slots) -> str | None:
    """
    Build DuckDB window/pivot SQL from slots.
    Returns None if intent doesn't require window functions.
    """
    if intent == "RUNNING_TOTAL":
        val = slots.value_keyword or "grand_total"
        grp = slots.group_by or "posting_date"
        return f"SELECT {grp}, {val}, SUM({val}) OVER (ORDER BY {grp}) AS running_total FROM t"

    if intent == "RANK":
        val = slots.value_keyword or "grand_total"
        grp = slots.group_by or "customer_name"
        n   = slots.limit_n or 10
        return (
            f"SELECT {grp}, {val}, "
            f"RANK() OVER (ORDER BY {val} DESC) AS rank FROM t "
            f"WHERE rank  dict | None:
    """
    Layer −1 (runs before PatternEngine): detect window function intent.
    Fetches base rows via Schema Compiler, then applies DuckDB window SQL in-process.
    Returns None if question doesn't require DuckDB.
    """
    from f_genbi.f_genbi.genbi.duckdb_engine import is_available, build_window_sql, run_window_query
    if not is_available():
        return None
    if not _DUCKDB_KEYWORDS.search(question):
        return None

    # 1. Detect window intent
    intent = _detect_window_intent(question)
    if not intent:
        return None

    # 2. Get base rows via Schema Compiler (no window functions — plain SELECT)
    slots = self._schema_parser.parse(question, chat_history)
    if not slots:
        return None
    base_sql, _ = NeuralSQLBuilder(slots, self._settings).build()
    if not base_sql:
        return None

    # 3. Execute base SQL → rows
    rows, _ = _execute_query(base_sql, max_rows=5000)
    if not rows:
        return None

    # 4. Run window SQL in DuckDB
    window_sql = build_window_sql(intent, slots)
    if not window_sql:
        return None

    result_rows = run_window_query(rows, window_sql)
    if result_rows is None:
        return None

    return self._build_done(question, base_sql + "\n-- window: " + window_sql,
                            result_rows, list(result_rows[0].keys()),
                            layer="duckdb", confidence=0.95)
```

**Acceptance criteria:**
- [ ] "running total of sales by month" → DuckDB layer fires, correct cumulative column
- [ ] "rank top customers by revenue" → DuckDB RANK() correct
- [ ] "percentile distribution of invoice amounts" → p25/p50/p75/p90 returned
- [ ] Non-window questions skip DuckDB entirely (no overhead)
- [ ] DuckDB layer not available → normal layers run unchanged

# F-GenBI Neural Engine — Master Plan v2

> **Document Type:** Implementation Master Plan
> **Status:** Approved for Development
> **Version:** 2.0 (supersedes initial neural engine plan)
> **Created:** 2026-04-13
> **Phase:** Phase 5 (Neural Engine) of F-GenBI

---

## Problem Statement

The existing `LocalNLPEngine` (Phase 1) works for ~70% of queries but has a hard ceiling:

1. `SQLTemplateEngine` only supports 6 rigid SQL shapes — anything outside breaks
2. `PatternEngine` has 24 hardcoded patterns — expanding requires developer intervention
3. No handling for custom DocTypes (company-specific fields unknown to the system)
4. No handling for multi-hop queries (AND/OR/BUT NOT across DocTypes)
5. Indian currency units (lakh, crore) not parsed
6. Coverage tops out at ~70% — the remaining 30% falls back to LLM or fails

**Goal:** Build a new `NeuralEngine` that achieves ≥99% coverage at ≥92% accuracy, fully offline, air-gapped, with no LLM API, no internet, and no manual setup.

---

## Architecture Summary

### Three Tiers of Capability

```
TIER 1 — Zero Setup (works on Day 1 after bench install-app)
  Schema-Driven Compiler — no models, no training, pure rules + live Frappe meta
  Coverage: ~75% | Accuracy: ~78%

TIER 2 — Trained (auto-trains from user feedback, no manual steps)
  Neural Slot Filler (DistilBERT-tiny ONNX, 20ms) + NeuralSQLBuilder
  T5-small Seq2Seq fallback (500ms)
  Coverage: ~97% | Accuracy: ~88-92%

TIER 3 — Turbo (optional — requires frappe_rpg or f_lightning)
  Rust acceleration (f_genbi_rs), RPG query analysis, Lightning MeiliSearch + NLP
  Coverage: ~99.5% | Accuracy: ~93-96%
```

### Full Layer Stack

```
Question → NeuralEngine.process()
  │
  ├── Layer 0: PatternEngine (24 patterns, regex DFA, ~40% queries)      100% accurate
  ├── Layer 1: Schema-Driven Compiler (pure rules, any DocType, Day 1)   ~78% accurate
  ├── Layer 2: Neural Slot Filler + NeuralSQLBuilder (ONNX, ~20ms)       ~88% accurate
  ├── Layer 3: T5-small Seq2Seq (ONNX, ~500ms, optional)                 ~80% accurate
  └── Layer 4: Interactive Clarification (deterministic dialog)           100% user-verified
```

## Key Design Decisions

### 1. Standalone — local_engine.py is Never Touched
The NeuralEngine is a new class in `neural_engine.py`. The existing Local NLP Engine path is preserved exactly.

### 2. Own Rust Module (f_genbi_rs)
f_genbi ships its own PyO3 Rust module (`rust/src/`) following the exact same conventions as `frappe_rpg/rust/`. This is self-contained — does not need frappe_rpg.

### 3. Optional Dependencies via Soft Imports
frappe_rpg and f_lightning are checked via `frappe.get_installed_apps()` and `try: import`. Never hard-required.

### 4. Models Stored in Site Data
ONNX models saved to `sites/{site}/neural_models/` — persists across `bench update`, survives app code updates.

### 5. Pre-Trained Model Ships With App
`f_genbi/models/slot_filler_base.onnx` committed to the release. Users get a working model from Day 1 without training anything.

### 6. Auto Training — Nobody Runs Scripts
The weekly scheduler runs incremental fine-tuning automatically from 👍 feedback. ONNX hot-swapped atomically. bench restart not needed.

## frappe_rpg Integration

**What it provides (all already built, read from `frappe_rs`):**

```python
import frappe_rs

# SQL quality check — before executing
plan = json.loads(frappe_rs.query_plan(sql))
# → {"grade": "A", "warnings": [], "cacheable": true}

# Safe rewrite — LIMIT injection, whitespace normalise
sql  = json.loads(frappe_rs.query_rewrite(sql, 500))["rewritten"]

# In-process L1 cache (faster than Redis for repeat queries)
cached = json.loads(frappe_rs.query_cache_get(sql))
if cached["hit"]:
    return json.loads(cached["result"])

# Better forecasting (Holt-Winters > LinearRegression)
forecast = frappe_rs.holtwinters_forecast(data_json, periods=6, alpha=0.3, beta=0.1, gamma=0.1)

# Polars-powered aggregation (faster than MySQL for large datasets)
agg = frappe_rs.aggregate_sales_data(rows_json)

# SQL quality analysis
explain = frappe_rs.explain_analyse(explain_json)
# → detects full table scans, filesort, temp tables
```

**Activation:** Only when `neural_engine_provider == "Neural + RPG Boost"` and `frappe_rpg` is installed.

# f_genbi Pre-trained Base Models

This directory ships with the app and provides Day-1 neural engine support
without requiring any user training data.
