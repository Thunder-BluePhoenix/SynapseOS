### Frappe Pulse

Offline-first event sync engine for distributed Frappe nodes.

### Installation

You can install this app using the [bench](https://github.com/frappe/bench) CLI:

```bash
cd $PATH_TO_YOUR_BENCH
bench get-app $URL_OF_THIS_REPO --branch develop
bench install-app frappe_pulse
```

This app uses `pre-commit` for code formatting and linting. Please [install pre-commit](https://pre-commit.com/#installation) and enable it for this repository:

```bash
cd apps/frappe_pulse
pre-commit install
```

Pre-commit is configured to use the following tools for checking and formatting your code:

- ruff
- eslint
- prettier
- pyupgrade

This app can use GitHub Actions for CI. The following workflows are configured:

- CI: Installs this app and runs unit tests on every push to `develop` branch.

# Motto

> **"Keep the pulse alive — online or off."**

frappe-pulse exists because ERP should work in a shop with no internet, a warehouse in a dead zone, and a field office that syncs once a day.

Every node keeps beating. Every event is remembered. Nothing is lost.

---

**Core beliefs:**

- Every device is a node, not a client
- Events are truth — not table rows
- Offline is a first-class state, not an error
- Sync should be silent, automatic, and conflict-aware
- Cheap hardware should run enterprise ERP

# Phase 1 — Event Bus

**Goal:** Every DocType change in Frappe becomes a structured event stored in a local event log.

---

## Deliverables

- [ ] `Pulse Event Log` DocType
- [ ] CDC hooks wired into Frappe document lifecycle
- [ ] Background worker that processes queued events
- [ ] Admin UI to view event stream

---

## DocType: Pulse Event Log

| Field | Type | Notes |
|-------|------|-------|
| `event_id` | Data | UUID, auto-generated |
| `event_type` | Select | CREATE / UPDATE / DELETE / SUBMIT / CANCEL |
| `doc_type` | Data | e.g. Sales Invoice |
| `doc_name` | Data | e.g. INV-0001 |
| `payload` | JSON | Full doc snapshot at event time |
| `node_id` | Data | Which node produced this event |
| `timestamp` | Datetime | Event creation time (UTC) |
| `sync_status` | Select | PENDING / SYNCED / FAILED |
| `checksum` | Data | SHA256 of payload (tamper detection) |

---

## CDC Hooks

Wire into Frappe document events:

```python
# hooks.py
doc_events = {
    "*": {
        "after_insert": "frappe_pulse.events.capture.on_create",
        "on_update": "frappe_pulse.events.capture.on_update",
        "on_submit": "frappe_pulse.events.capture.on_submit",
        "on_cancel": "frappe_pulse.events.capture.on_cancel",
        "on_trash": "frappe_pulse.events.capture.on_delete",
    }
}
```

---

## Background Worker

- Runs via Frappe's RQ (Redis Queue)
- Picks up PENDING events
- Marks them SYNCED or FAILED
- Retry on failure (exponential backoff)

---

## Success Criteria

- Create a Sales Invoice → event appears in Pulse Event Log instantly
- Event contains full payload, node_id, timestamp, checksum
- Worker processes event within 2 seconds under normal load
- 10,000 events stored with no performance degradation

# Phase 2 — Sync Engine

**Goal:** Two Frappe nodes can exchange events and stay in sync over HTTP, with retry logic and sync status tracking.

---

## Deliverables

- [ ] `Pulse Node` DocType (node registry)
- [ ] Sync push endpoint (send events to remote node)
- [ ] Sync pull endpoint (receive events from remote node)
- [ ] Sync worker (scheduled, runs every N minutes)
- [ ] Sync log + status dashboard

---

## DocType: Pulse Node

| Field | Type | Notes |
|-------|------|-------|
| `node_id` | Data | UUID, unique per site |
| `node_name` | Data | Human label (e.g. "Shop A") |
| `endpoint_url` | Data | Remote Frappe URL |
| `api_key` | Password | Auth token for this node |
| `sync_direction` | Select | PUSH / PULL / BIDIRECTIONAL |
| `last_synced_at` | Datetime | Last successful sync |
| `sync_status` | Select | ACTIVE / PAUSED / ERROR |

---

## Sync Flow

```
Node A                          Node B
  |                                |
  |-- GET /pulse/events?after=X -->|
  ||
  |   (push local pending events)  |
  |&node_id=
POST /api/method/frappe_pulse.sync.receive   (body: event batch)
GET  /api/method/frappe_pulse.sync.status    (node health check)
```

---

## Sync Worker

- Scheduled via Frappe scheduler (every 5 min default, configurable)
- For each registered node:
  1. Pull new events from remote
  2. Apply locally (skip duplicates by event_id)
  3. Push local PENDING events
  4. Update `last_synced_at`
- On failure: mark node ERROR, retry after backoff

---

## Schema Migration Handling

When a DocType gains a new field (Frappe upgrade or customization), old events in the log carry the old schema. A node on an older version will receive events it cannot fully apply.

**The problem:**
```
HQ upgrades Frappe → Sales Invoice gets new field "GST Category"
Shop A is offline, still on old version
Shop A receives new-schema events → crashes or silently drops field
```

**Solution: Schema version in every event**

Add `schema_version` to the event payload:
```json
{
  "event_id": "uuid",
  "doc_type": "Sales Invoice",
  "schema_version": "15.2.1",
  "payload": { ... }
}
```

**Apply rules on receiving node:**

| Situation | Action |
|-----------|--------|
| Same schema version | Apply normally |
| Receiver is newer | Apply — extra fields ignored safely |
| Receiver is older | Queue event as `SCHEMA_MISMATCH`, do not apply |
| `SCHEMA_MISMATCH` backlog | Auto-retry after node upgrade |

**DocType: Pulse Node — new field:**

| Field | Type | Notes |
|-------|------|-------|
| `frappe_version` | Data | Reported by node on each sync handshake |
| `schema_mismatch_count` | Int | Events held back due to schema gap |

**Admin visibility:**
- `SCHEMA_MISMATCH` events visible in event log with clear reason
- Node card in dashboard shows schema lag warning if mismatch count > 0
- Events auto-applied once node upgrades and schema version matches

---

## Success Criteria

- Two local Frappe sites sync events bidirectionally
- Duplicate events are idempotent (applying twice = same result)
- Network failure → events queue up → sync completes when connection returns
- Sync 1,000 events between nodes in under 10 seconds
- New-schema event received by old-node → queued as SCHEMA_MISMATCH, not dropped or crashed
- After node upgrade → SCHEMA_MISMATCH events auto-applied correctly

# Phase 3 — Conflict Resolution

**Goal:** When two nodes modify the same document while offline, frappe-pulse detects the conflict and resolves it — automatically where safe, manually where not.

---

## Deliverables

- [ ] Conflict detection on event apply
- [ ] `Pulse Conflict` DocType
- [ ] Three resolution strategies (configurable per DocType)
- [ ] Manual resolution UI in Frappe desk
- [ ] Conflict audit log

---

## When Conflicts Happen

```
Node A (offline)         Node B (offline)
  └─ Updates INV-001       └─ Updates INV-001
     amount: 500              amount: 600

Both come online → who wins?
```

---

## DocType: Pulse Conflict

| Field | Type | Notes |
|-------|------|-------|
| `conflict_id` | Data | UUID |
| `doc_type` | Data | e.g. Sales Invoice |
| `doc_name` | Data | e.g. INV-001 |
| `local_event_id` | Link | Pulse Event Log |
| `remote_event_id` | Link | Pulse Event Log |
| `conflicting_fields` | JSON | Which fields differ |
| `resolution_strategy` | Select | AUTO_LAST_WRITE / FIELD_MERGE / MANUAL |
| `resolved_by` | Link | User (if manual) |
| `resolved_at` | Datetime | |
| `status` | Select | PENDING / RESOLVED |

---

## Resolution Strategies

### Strategy A: Last Write Wins (default, simple)
- Compare timestamps
- Latest event overwrites
- Risk: silent data loss on financial fields

### Strategy B: Field-Level Merge (recommended)
- Non-conflicting fields → merge both
- Conflicting fields → flag only those fields
- Example: Node A changed `remarks`, Node B changed `amount` → both apply safely

### Strategy C: Manual Resolution
- Flag the conflict
- Show diff to user
- User picks winner per field
- Required for: `amount`, `grand_total`, `qty`, any financial field

---

## DocType-Level Config

```json
{
  "Sales Invoice": {
    "default_strategy": "MANUAL",
    "field_overrides": {
      "remarks": "LAST_WRITE",
      "grand_total": "MANUAL"
    }
  }
}
```

---

## Success Criteria

- Two nodes modify same doc → conflict detected, not silently overwritten
- Field-merge applies correctly on non-overlapping field changes
- Manual resolution UI shows clear before/after diff
- All resolutions logged in audit trail

# Phase 4 — Rust Core

**Goal:** Replace Python bottlenecks with a Rust library (via PyO3) for event serialization, log compaction, and checksum computation.

---

## Deliverables

- [ ] Rust crate: `pulse_core`
- [ ] PyO3 bindings exposed to Python
- [ ] Event serialization (JSON → binary, binary → JSON)
- [ ] Event log compaction (squash old events per doc)
- [ ] Checksum computation (SHA256 per event payload)
- [ ] Benchmarks: Rust vs Python for each operation

---

## Why Rust Here

| Operation | Python | Rust (estimate) |
|-----------|--------|-----------------|
| Serialize 10k events | ~800ms | ~40ms |
| Compact 100k event log | ~12s | ~300ms |
| SHA256 10k payloads | ~600ms | ~30ms |

At scale (rural node processing backlogs), this matters.

---

## Rust Crate Structure

```
pulse_core/
├── Cargo.toml
├── src/
│   ├── lib.rs           # PyO3 module entry
│   ├── event.rs         # Event struct + serde
│   ├── compaction.rs    # Log compaction logic
│   └── checksum.rs      # SHA256 helpers
```

---

## PyO3 Binding Example

```rust
#[pyfunction]
fn serialize_event(event_json: &str) -> PyResult> {
    let event: PulseEvent = serde_json::from_str(event_json)?;
    Ok(bincode::serialize(&event).unwrap())
}

#[pyfunction]
fn compact_log(events_json: &str) -> PyResult {
    // Keep only latest event per (doc_type, doc_name)
    // Return compacted list as JSON
}
```

---

## Log Compaction Logic

For long-running nodes, the event log grows unbounded.

Compaction rules:
- Keep last event per `(doc_type, doc_name)` for SYNCED events older than 30 days
- Never compact PENDING or FAILED events
- Never compact DELETE events (they must replay correctly)
- Write compaction checkpoint to disk before pruning

---

## Integration Point

Python calls Rust via PyO3:

```python
# frappe_pulse/events/capture.py
from pulse_core import serialize_event, compute_checksum

payload_bytes = serialize_event(doc_as_json)
checksum = compute_checksum(payload_bytes)
```

---

## Success Criteria

- Rust library builds cleanly via `maturin develop`
- All three operations (serialize, compact, checksum) benchmarked
- Python integration tests pass using Rust backend
- 10x+ speedup over pure Python on compaction

# Phase 5 — Go Transport

**Goal:** Replace the HTTP-based sync with a Go binary that handles node discovery, persistent connections, binary event transport, and connection pooling.

---

## Deliverables

- [ ] Go binary: `pulse-transport`
- [ ] Binary sync protocol (replaces JSON over HTTP)
- [ ] Node discovery (LAN broadcast + manual registry)
- [ ] Connection pool (persistent node connections)
- [ ] Frappe → Go bridge (Python calls Go via subprocess or socket)
- [ ] "Internet-in-a-Box" mode (local WiFi mesh)

---

## Why Go Here

| Concern | Python HTTP | Go Transport |
|---------|-------------|-------------|
| Concurrent node connections | Slow, thread-per-conn | Goroutines, cheap |
| Binary protocol | Not native | Native |
| LAN node discovery | Complex | UDP broadcast, simple |
| Long-lived connections | Heavy | Lightweight |
| Single deployable binary | No | Yes |

---

## Go Binary Structure

```
pulse-transport/
├── main.go
├── protocol/
│   ├── frame.go         # Binary frame format
│   └── codec.go         # Encode/decode events
├── transport/
│   ├── server.go        # Listen for incoming nodes
│   ├── client.go        # Connect to remote nodes
│   └── pool.go          # Connection pool
├── discovery/
│   ├── broadcast.go     # UDP LAN discovery
│   └── registry.go      # Static node list fallback
└── bridge/
    └── socket.go        # Unix socket bridge to Python
```

---

## Binary Protocol (Frame Format)

```
[ 4 bytes: frame_len ][ 1 byte: msg_type ][ N bytes: payload (bincode) ]

msg_type:
  0x01 = HANDSHAKE
  0x02 = EVENT_BATCH
  0x03 = ACK
  0x04 = PING
  0x05 = CONFLICT_NOTIFY
```

---

## Node Discovery

**LAN mode (no internet needed):**
- UDP broadcast on port 7979
- Nodes announce: `{ node_id, node_name, endpoint }`
- Auto-register discovered nodes

**Manual mode:**
- Static list in `pulse_node` DocType
- Go binary reads from Frappe API on start

---

## Python ↔ Go Bridge

Frappe calls Go transport via Unix socket:

```python
# frappe_pulse/transport/client.py
import socket, json

def send_events_to_node(node_id: str, events: list):
    sock = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
    sock.connect("/tmp/pulse-transport.sock")
    sock.send(json.dumps({"node_id": node_id, "events": events}).encode())
```

---

## Internet-in-a-Box Mode

One device becomes a local hub:
- Go binary acts as server
- Other devices on same WiFi connect directly
- No internet required
- Sync to cloud when internet returns

---

## Success Criteria

- Go binary syncs 10,000 events between two nodes in under 3 seconds
- LAN discovery finds nodes on same network automatically
- Binary protocol uses 60%+ less bandwidth than JSON/HTTP
- Python bridge works transparently (Python code unchanged)
- Single binary deployable on Linux ARM (Raspberry Pi target)

## Sync Queue Durability

Events written to SQLite before returning from the hook:

def on_create(doc, method):

Even if the process crashes mid-sync, SQLite has the event. Nothing lost.

## C Layer: SQLite Custom Extensions

The only place C belongs in frappe-pulse is here — SQLite's extension API is C-only. No other layer needs it.

**Two targeted extensions:**

### 1. Encrypted Event Log (SQLite VFS)
SQLite's Virtual File System (VFS) layer intercepts all read/write calls. A custom C VFS encrypts the event log at rest on edge nodes — critical for retail devices that can be physically stolen.

```c
/* pulse_vfs.c — custom SQLite VFS for AES-256 encryption */
static int pulseVfsRead(sqlite3_file *pFile, void *zBuf, int iAmt, sqlite3_int64 iOfst) {
    PulseVfsFile *p = (PulseVfsFile *)pFile;
    int rc = p->pReal->pMethods->xRead(p->pReal, zBuf, iAmt, iOfst);
    if (rc == SQLITE_OK) aes256_decrypt(zBuf, iAmt, p->key);
    return rc;
}
```

Loaded as a SQLite extension — no changes to any other layer.

### 2. Fast Checksum Function (SQLite scalar function)
Register a custom `pulse_checksum(payload)` SQL function in C for computing SHA-256 directly inside SQLite queries — faster than computing in Python or Rust after fetch.

```c
/* pulse_checksum.c */
static void pulseChecksumFunc(sqlite3_context *ctx, int argc, sqlite3_value **argv) {
    const unsigned char *data = sqlite3_value_blob(argv[0]);
    int len = sqlite3_value_bytes(argv[0]);
    unsigned char hash[32];
    sha256(data, len, hash);
    sqlite3_result_blob(ctx, hash, 32, SQLITE_TRANSIENT);
}
```

**Scope rule:** These are the only two C files in the entire project. Thin, targeted, no manual memory management beyond what SQLite's API requires.

## 1. Selective Sync / Data Partitioning

Without this, every node gets all data. A 10-shop chain means every shop device holds all 10 shops' invoices — wrong for performance and data isolation.

### DocType: Pulse Sync Scope

| Field | Type | Notes |
|-------|------|-------|
| `node` | Link → Pulse Node | Which node this scope applies to |
| `doc_type` | Data | e.g. Sales Invoice |
| `enabled` | Check | Whether this DocType syncs to this node |
| `filter_field` | Data | e.g. `warehouse`, `branch`, `cost_center` |
| `filter_value` | Data | e.g. `Stores - Shop A` |
| `sync_direction` | Select | PUSH / PULL / BIDIRECTIONAL |

**Example scope config for Shop A:**
```
Sales Invoice   → filter: branch = "Shop A"   → BIDIRECTIONAL
Customer        → filter: none (all customers) → PULL only
Salary Slip     → disabled (Shop A never sees payroll)
Stock Entry     → filter: warehouse = "Shop A Warehouse" → BIDIRECTIONAL
```

### How It Works

On pull request from Node A:
```python
def get_events_for_node(node_id, after_timestamp):
    scopes = get_sync_scopes(node_id)
    events = get_pending_events(after=after_timestamp)

    return [
        e for e in events
        if scope_allows(e, scopes)
    ]
```

Server filters events before sending — node never receives data outside its scope.

### Scope Inheritance

Nodes can inherit a scope template:
- `DocType: Pulse Scope Template` — define once, apply to many nodes
- E.g. "Retail Shop Template" applied to all 20 shop nodes
- Override individual rules per node as needed

## 3. Event Replay

The "undo" for distributed ERP. Replay events from any checkpoint to rebuild correct state — for debugging, disaster recovery, or auditing.

### Replay API

```
POST /api/method/frappe_pulse.replay.start
{
  "doc_type": "Sales Invoice",       # optional: scope to one DocType
  "doc_name": "INV-001",             # optional: scope to one document
  "from_timestamp": "2026-04-01",    # replay from this point
  "to_timestamp":   "2026-04-30",    # optional end point
  "target_node": "node-uuid",        # which node to replay on
  "dry_run": true                    # preview without applying
}
```

**Dry run response:**
```json
{
  "events_to_replay": 143,
  "estimated_duration_seconds": 8,
  "conflicts_detected": 2,
  "preview": [...]
}
```

### Replay Worker

- Runs as a background job (not blocking)
- Applies events in strict timestamp order
- Skips already-applied events (idempotent)
- Pauses on conflict → logs for review → continues or stops (configurable)
- Progress tracked in `Pulse Replay Job` DocType

### DocType: Pulse Replay Job

| Field | Type | Notes |
|-------|------|-------|
| `job_id` | Data | UUID |
| `status` | Select | QUEUED / RUNNING / PAUSED / COMPLETE / FAILED |
| `events_total` | Int | |
| `events_applied` | Int | |
| `events_skipped` | Int | |
| `conflicts_hit` | Int | |
| `started_at` | Datetime | |
| `completed_at` | Datetime | |
| `initiated_by` | Link → User | |

### Use Cases

- **Disaster recovery:** Node corrupted → wipe local DB → replay from event log → back to correct state
- **Debugging:** "Why does Shop A show wrong stock?" → replay stock entries for that item → find the bad event
- **Audit:** Replay a document's full history to see every change and who made it

---

## 4. Event Retention & Compaction Policy

Events shouldn't accumulate forever — but some must never be deleted.

### DocType: Pulse Retention Policy

| Field | Type | Notes |
|-------|------|-------|
| `doc_type` | Data | e.g. Sales Invoice |
| `retention_days` | Int | Delete SYNCED events older than N days |
| `never_delete` | Check | Overrides retention (compliance) |
| `compaction_enabled` | Check | Allow Rust compaction for this DocType |
| `archive_before_delete` | Check | Write to archive file before purging |

**Defaults:**

| DocType category | Default retention | Notes |
|-----------------|------------------|-------|
| Financial (Invoice, Payment) | Never delete | Compliance |
| Stock movements | 365 days | |
| Master data (Customer, Item) | Never delete | |
| Logs, notifications | 30 days | |
| Draft documents | 7 days | |

### Compaction Rules

Rust compaction (Phase 4) runs based on policy:
- Only compacts SYNCED events older than `retention_days`
- Never compacts PENDING / FAILED / SCHEMA_MISMATCH
- Never compacts DocTypes with `never_delete = true`
- Archives to `.jsonl.gz` file before deleting if `archive_before_delete = true`

### Retention Worker

- Runs nightly via Frappe scheduler
- Reads policies → deletes eligible events → logs compaction run
- Reports: events deleted, space freed, DocTypes compacted

---

## Success Criteria

- Shop A node only receives events matching its sync scope (no other branch data)
- Scope change in Frappe desk → takes effect on next sync cycle
- Dashboard shows all node statuses updated within 60 seconds
- Lag alert fires when node falls more than 10 minutes behind
- Event replay rebuilds correct document state from checkpoint
- Dry-run replay shows accurate preview without modifying data
- Retention policy runs nightly without manual intervention
- Financial DocTypes never deleted regardless of retention setting
- Schema mismatch count visible per node in dashboard

## Architecture

```
Flutter app (online)
        ↓  POST /api/sync/receive   (batch of events)
frappe-pulse receive endpoint
        ↓  apply_event() → 'applied'
        ↓  frappe.enqueue(notify_event)   ← async, no latency
Mobile push worker
        ↓  FCM v1 API / APNs HTTP/2
Device receives notification
        ↓  tap → deep-link → DetailScreen(doctype, name)
```

```
Flutter app (online, pull)
        ↓  GET /api/sync/pull?_mobile=1&after=...
frappe-pulse pull endpoint
        ↓  filter by scope (Phase 7)
        ↓  strip_payload() → removes non-essential fields
        ↓  encode_mobile_response() → MessagePack bytes
Flutter app
        ↓  msgpack.decode() → typed PulseEvent list
```

## Pulse Push Config

Configure in Frappe desk → Pulse Push Config:

| Field | Purpose |
|-------|---------|
| FCM Server Key | Firebase service account JSON (v1 API) |
| Firebase Project ID | e.g. `my-frappe-app` |
| APNs Key ID | From Apple Developer portal |
| Apple Team ID | 10-character team identifier |
| App Bundle ID | e.g. `com.yourcompany.frappe` |
| APNs Private Key | Contents of `.p8` file |
| Notify on DocTypes | Blank = all; or list specific ones |
| Event Types | ALL / CREATE / UPDATE / SUBMIT / CANCEL |

FCM handles both Android and iOS delivery. APNs direct is optional (for iOS apps that don't use Firebase).

---

## Bandwidth Optimization (?_mobile=1)

| Without `?_mobile=1` | With `?_mobile=1` |
|----------------------|-------------------|
| Full JSON payload | Field-stripped payload |
| All audit fields included | `creation`, `modified_by`, `__islocal`, etc. stripped |
| JSON encoding | MessagePack binary (~30% smaller) |
| ~8KB per event avg | ~3KB per event avg |

Fields always kept: `name`, `doctype`, `status`, `company`, `customer`, `grand_total`, `posting_date`, and other display-critical fields.

# frappe-pulse — Build Plan

**One line:** Offline-first event sync engine for distributed Frappe nodes.

---

## What We Are Building

A three-layer system on top of Frappe Framework:

```
Frappe (Python)
    ↓ PyO3
Rust core — event serialization, log compaction, conflict resolution
    ↓
Go transport — node discovery, connection management, sync protocol
```

---

## What We Are NOT Building

- A WebView mobile wrapper
- A Kafka cluster dependency
- A replacement for Frappe's database
- A cloud-only product

---

## Phases Overview

| Phase | Name | Output |
|-------|------|--------|
| 1 | Event Bus | CDC hooks + event log DocType + background worker |
| 2 | Sync Engine | Node-to-node sync over HTTP, retry logic |
| 3 | Conflict Resolution | Field-level merge + manual resolution UI |
| 4 | Rust Core | Fast serialization + event log compaction via PyO3 |
| 5 | Go Transport | Binary sync protocol, node discovery, connection pooling |
| 6 | Offline Node | SQLite-backed edge node, full offline operation |

---

## Tech Stack

| Layer | Language | Reason |
|-------|----------|--------|
| Frappe hooks, DocTypes, API | Python | Tight Frappe integration |
| Event serialization, compaction | Rust + PyO3 | Speed, zero-copy, serde |
| Node transport, sync protocol | Go | Goroutines, net package |
| Edge node local DB | SQLite | Lightweight, no server needed |

---

## Target Users

- Small retail chains (2–20 shops)
- Warehouses with poor connectivity
- Rural businesses running ERPNext
- Field teams needing offline ERP access

---

## Non-Goals (for now)

- Mobile app UI (that comes after Phase 6)
- Zero-Trust access layer (separate product: frappe-gate)
- Full Kafka integration (event protocol will be compatible later)
