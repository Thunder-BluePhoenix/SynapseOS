# Motto

> **"Trust nothing. Verify everything. Let only the right ones through."**

frappe-gate exists because most self-hosted ERPNext deployments are one exposed port away from a breach. API keys get leaked. Sessions get stolen. Devices get shared.

Zero-Trust means: no device, no user, no network is trusted by default — ever. Every request is verified, every session is short-lived, every access is logged.

---

**Core beliefs:**

- Device identity is not optional — a username/password is not enough
- Every API call is an access decision, not just an authentication check
- Audit logs are not a feature — they are the product
- Self-hosted should not mean insecure
- A proxy that requires a PhD to configure is not a security product

## Token Design

**Algorithm:** ECDSA (ES256) — smaller and faster than RSA

**Claims:**
```json
{
  "sub": "user@example.com",
  "device_id": "uuid-of-device",
  "node_id": "uuid-of-node",
  "roles": ["Sales User", "Stock User"],
  "fingerprint_hash": "sha256-of-device-fingerprint",
  "ip_binding": "203.0.113.5",
  "iat": 1710000000,
  "exp": 1710003600
}
```

**TTL:** 1 hour (configurable)
**Refresh:** Allowed up to 7 days from issuance without re-registration

---

## Session Binding

Token theft is the biggest risk with JWT. Session binding closes that hole.

**How it works:**
- On token issuance: hash the device fingerprint + client IP → embed in token claims
- On every request: recompute hash from incoming request → compare with token claim
- Mismatch = token stolen and used from different device/network → reject

```go
func verifySessionBinding(claims JWTClaims, r *http.Request) bool {
    incomingFingerprint := r.Header.Get("X-Device-Fingerprint")
    incomingIP := extractClientIP(r)
    expectedHash := sha256(incomingFingerprint + claims.IPBinding)
    return claims.FingerprintHash == expectedHash
}
```

**IP binding modes** (configurable per device type):
| Mode | Use case |
|------|---------|
| `strict` | Fixed IP (warehouse terminal, shop POS) |
| `subnet` | Same /24 network allowed (office WiFi) |
| `none` | Field agents, mobile workers |

```

  |                           |                       |
  |-- POST /gate/device/register (fingerprint, pubkey)|
  |                           |-- validate user creds→|
  |                           ||
  |<-- { device_id, status: PENDING } ----------------|

  |-- POST /gate/token (device_id + signature) --------|
  |<-- { access_token, expires_in } ------------------|
```

## Token Verification Middleware

Every request through the proxy:

```go
func TokenMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        token := extractToken(r)
        if token == "" {
            http.Error(w, "no token", 401)
            return
        }
        claims, err := verifyToken(token)
        if err != nil {
            http.Error(w, "invalid token", 401)
            return
        }
        // inject claims into request context
        ctx := withClaims(r.Context(), claims)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}
```

## Revocation

- Admin sets device status to `REVOKED` in Frappe desk
- frappe-gate polls revocation list every 60 seconds (or webhook push)
- Revoked `device_id` rejected immediately, even with valid token
- In-memory revocation cache — no DB hit per request

## Emergency Lockdown Mode

One command kills all active sessions site-wide instantly:

```bash
frappe-gate lockdown --reason "suspected breach"
```

**What it does:**
- Sets a global `lockdown` flag in gate's in-memory state
- All token verifications return `423 Locked` immediately
- No request reaches Frappe during lockdown
- Logs the event with timestamp + reason to audit log
- Writes lockdown record to `Gate Audit Log` DocType

**Lifting lockdown:**
```bash
frappe-gate lockdown --lift
```
- Clears the flag
- Forces all devices to re-authenticate (clears token cache)
- Lockdown duration logged

**Admin UI trigger:**
- One-click lockdown button in Frappe desk (Gate Settings page)
- Requires System Manager role
- Confirmation dialog with mandatory reason field

## Policy Rule Structure

```yaml
# Evaluated in priority order

- policy: "Sales Team Access"
  role: "Sales User"
  allow:
    - path: "/api/resource/Sales Invoice*"
      methods: [GET, POST]
    - path: "/api/resource/Customer*"
      methods: [GET, POST, PUT]
    - path: "/app/sales*"
      methods: [GET]

- policy: "Read Only Guest"
  role: "Guest"
  allow:
    - path: "/api/method/frappe.auth.get_logged_user"
      methods: [GET]

- policy: "Default Deny"
  role: "*"
  deny: "*"
```

---

## Policy Evaluation Order

```
Request arrives
      ↓
Extract roles from JWT claims
      ↓
Load policies for those roles (from cache)
      ↓
Evaluate in priority order:
  - Match path pattern?
  - Match HTTP method?
  - Within time restriction?
  - IP in whitelist? (if set)
      ↓
First match wins → ALLOW or DENY
      ↓
No match → DENY (default)
```

---

## Go Policy Engine

```go
type PolicyEngine struct {
    policies []Policy       // sorted by priority
    mu       sync.RWMutex
}

func (pe *PolicyEngine) Allow(roles []string, method, path string) bool {
    pe.mu.RLock()
    defer pe.mu.RUnlock()

    for _, policy := range pe.policies {
        if policy.MatchesRole(roles) && policy.MatchesRoute(method, path) {
            return policy.Effect == "allow"
        }
    }
    return false // default deny
}
```

# Phase 5 — mTLS Tunnels

**Goal:** Mutual TLS between frappe-gate and Frappe backend, and between frappe-gate nodes. Both sides verify each other's identity — not just the client verifying the server.

---

## Deliverables

- [ ] Internal CA (Certificate Authority) — self-managed, no external dependency
- [ ] Gate → Frappe mTLS (backend connection secured)
- [ ] Gate ↔ Gate mTLS (node-to-node, for frappe-pulse integration)
- [ ] Client certificate issuance for registered devices (optional, advanced)
- [ ] Certificate rotation (auto-renew before expiry)
- [ ] Cert revocation list (CRL) management

---

## Why mTLS

Standard TLS: client verifies server identity.
mTLS: **both sides verify each other**.

```
Without mTLS:
  Anyone who knows the URL can hit Frappe directly (bypassing gate)

With mTLS (gate → Frappe):
  Frappe only accepts connections from frappe-gate
  Direct access = rejected (no valid client cert)
```

---

## Internal CA Design

frappe-gate generates and manages its own CA:

```
frappe-gate-ca/
├── ca.crt          ← Root CA cert (distribute to all nodes)
├── ca.key          ← Root CA private key (never leaves gate)
├── gate.crt        ← Gate's own cert (signed by CA)
├── gate.key        ← Gate's private key
└── issued/
    ├── node-a.crt
    └── node-b.crt
```

CA managed via CLI:

```bash
frappe-gate ca init
frappe-gate ca issue --node node-a
frappe-gate ca revoke --node node-a
frappe-gate ca list
```

---

## Gate → Frappe mTLS Config

```yaml
backend:
  url: "https://127.0.0.1:8000"
  mtls:
    enabled: true
    client_cert: "/etc/frappe-gate/gate.crt"
    client_key:  "/etc/frappe-gate/gate.key"
    ca_cert:     "/etc/frappe-gate/ca.crt"
```

Frappe nginx config requires client cert:

```nginx

ssl_verify_client on;
```

---

## Gate ↔ Gate mTLS (Node Mesh)

For frappe-pulse sync between nodes, each node's gate authenticates the other:

```
Node A frappe-gate          Node B frappe-gate
  |-- present node-a.crt -->|
  ||
```

---

## Certificate Rotation

- Certs issued with 90-day TTL
- Background goroutine checks expiry daily
- Auto-renews 14 days before expiry
- Rotation is zero-downtime (new cert loaded while old still valid)
- Rotation event logged to audit layer

---

## Go mTLS Setup

```go
func newMTLSClient(certFile, keyFile, caFile string) *http.Client {
    cert, _ := tls.LoadX509KeyPair(certFile, keyFile)
    caCert, _ := os.ReadFile(caFile)
    caCertPool := x509.NewCertPool()
    caCertPool.AppendCertsFromPEM(caCert)

    tlsConfig := &tls.Config{
        Certificates: []tls.Certificate{cert},
        RootCAs:      caCertPool,
        MinVersion:   tls.VersionTLS13,
    }
    return &http.Client{
        Transport: &http.Transport{TLSClientConfig: tlsConfig},
    }
}
```

## 1. Brute Force Shield

Rate limiting in Phase 4 blocks volume. Brute force shield targets credential stuffing and targeted attacks.

**Progressive delay on failed auth:**

| Failed attempts | Delay before next attempt |
|----------------|--------------------------|
| 1–3 | None |
| 4–5 | 2 second enforced wait |
| 6–8 | 10 second enforced wait |
| 9–10 | 60 second enforced wait |
| 11+ | Auto-block IP for 1 hour |

```go
type BruteForceTracker struct {
    attempts map[string]*AttemptRecord  // keyed by IP + username
    mu       sync.Mutex
}

func (bt *BruteForceTracker) RecordFailure(ip, username string) (delay time.Duration, blocked bool) {
    record := bt.getOrCreate(ip + ":" + username)
    record.Count++
    return bt.computeDelay(record.Count), record.Count > 10
}
```

**Auto-notify admin:**
- After 5 consecutive failures on same account → Frappe notification to System Manager
- After IP auto-block → logged to `Gate Security Event`

---

## 2. API Key → Token Migration

Most existing ERPNext setups use `Authorization: token api_key:api_secret`. frappe-gate must handle this gracefully or adoption dies.

**Migration phases:**

### Phase A: Detection + Warning (non-breaking)
- frappe-gate detects legacy `token api_key:api_secret` header
- Forwards the request (doesn't block yet)
- Logs warning: `"Legacy API key detected for user X — migrate to device token"`
- Admin sees migration status dashboard: X of Y integrations still on legacy auth

### Phase B: Soft Block (configurable cutover date)
- Admin sets `legacy_auth_cutover_date` in Gate Settings
- After that date: legacy requests get `401` with migration instructions in response body
- Per-integration exemption available (for external services that can't migrate)

- All legacy API keys rejected
- Only JWT device tokens accepted

  "api_secret": "yyy",
  "device_name": "My Integration"

## 3. Webhook Signature Verification

Frappe sends and receives webhooks (Razorpay, Stripe, GitHub, custom). frappe-gate intercepts all of them.

**Inbound webhooks (external → Frappe):**
- Gate verifies HMAC signature on incoming webhook
- Each webhook source configured with its secret in `Gate Webhook Config` DocType
- Invalid signature → `401` before reaching Frappe
- Prevents webhook spoofing (fake payment confirmations, etc.)

```go
func verifyWebhookSignature(secret, payload string, sig string) bool {
    mac := hmac.New(sha256.New, []byte(secret))
    mac.Write([]byte(payload))
    expected := hex.EncodeToString(mac.Sum(nil))
    return hmac.Equal([]byte(expected), []byte(sig))
}
```

**Outbound webhooks (Frappe → external):**
- Gate signs outgoing webhook payloads with site's private key
- Receiving systems can verify the webhook came from your site

**DocType: Gate Webhook Config:**

| Field | Type | Notes |
|-------|------|-------|
| `source_name` | Data | e.g. "Razorpay" |
| `path_pattern` | Data | e.g. `/api/method/payment.webhook*` |
| `signature_header` | Data | e.g. `X-Razorpay-Signature` |
| `secret` | Password | HMAC secret |
| `algorithm` | Select | SHA256 / SHA512 |
| `enabled` | Check | |

## 4. Geo-Fencing

Location-bound access for shop/warehouse devices. A POS terminal at Shop A should not be usable from a different city.

**Two modes:**

### IP Range Binding
- Device registered with allowed CIDR range
- Request from outside range → `403 Location Policy Violation`
- Suitable for fixed locations (shops, warehouses with static IPs)

### GPS Binding (Mobile)
- Device sends GPS coordinates in `X-Device-Location` header
- Gate checks coordinates against allowed radius in `Gate Device`
- Suitable for field agents with defined service areas

**DocType: Gate Device — Geo fields:**

| Field | Type | Notes |

| `allowed_lat` | Float | Center latitude (GPS mode) |
| `allowed_lng` | Float | Center longitude (GPS mode) |
| `allowed_radius_km` | Float | Allowed radius (GPS mode) |
| `allowed_ip_ranges` | Long Text | CIDR list (IP_RANGE mode) |

# frappe-gate — Build Plan

**One line:** Zero-Trust access proxy for self-hosted Frappe deployments.

---

## What We Are Building

A Go binary that sits in front of Frappe and enforces:
- Device-based authentication (not just username/password)
- Short-lived signed tokens (ECDSA JWT)
- Role-based network access policies
- Encrypted API tunnels (mTLS)
- Full audit log written back to Frappe

```
Client (browser / mobile / edge node)
        ↓ HTTPS
   frappe-gate  (Go binary)
   ├── verify device identity
   ├── validate short-lived token
   ├── check role → access policy
   ├── log every request
   └── forward to Frappe
        ↓
   Frappe (Python + MariaDB)
```

---

## What We Are NOT Building

- Not a VPN replacement (no full tunnel routing)
- Not a firewall (no packet-level filtering)
- Not cloud-dependent (fully self-hosted)
- Not an identity provider (Frappe handles users, gate handles devices)
- No Kubernetes / service mesh required

---

## Phases Overview

| Phase | Name | Output |
|-------|------|--------|
| 1 | Core Proxy | Go reverse proxy + TLS termination |
| 2 | Device Identity | Device registration, ECDSA JWT issuance |
| 3 | Policy Engine | Role → access rules, per-route enforcement |
| 4 | Audit Layer | Request logging, anomaly flags, Frappe write-back |
| 5 | mTLS Tunnels | Mutual TLS between gate and Frappe, client certs |
| 6 | Frappe Integration | DocTypes, admin UI, Cloud marketplace packaging |

---

## Tech Stack

| Layer | Tech | Reason |
|-------|------|--------|
| Proxy engine | Go `net/http` + `httputil.ReverseProxy` | Fast, single binary, goroutines |
| TLS / mTLS | Go `crypto/tls` | No OpenSSL dependency |
| Token signing | ECDSA JWT (`golang-jwt/jwt`) | Short-lived, tamper-proof |
| Policy engine | Go (in-process) | Fast evaluation, no external dep |
| Config | YAML + hot reload | Simple, no DB needed at proxy layer |
| Device registry | Frappe DocType | Source of truth lives in ERP |
| Audit log | Frappe REST API write-back | Audit trail in ERP, not sidecar |
| Deployment | Single Go binary + systemd | Works on $5 VPS or Raspberry Pi |

---

## Deployment Position

```
Internet
   ↓
Nginx (TLS termination, optional)
   ↓
frappe-gate :8080  ← YOU ARE HERE
   ↓
Frappe / Gunicorn :8000
```

Or replace Nginx entirely:

```
Internet
   ↓
frappe-gate :443  (handles TLS itself)
   ↓
Frappe :8000
```

---

## Target Users

- Self-hosted ERPNext on VPS (primary market)
- Edge nodes running frappe-pulse (device auth for sync nodes)
- Frappe Cloud users wanting add-on Zero-Trust layer
- Businesses with compliance requirements (audit trail)

---

## Companion Product

frappe-gate pairs directly with **frappe-pulse**:
- frappe-pulse handles sync between nodes
- frappe-gate handles who is allowed to connect to each node
- Together: secure, offline-capable, distributed ERP network
