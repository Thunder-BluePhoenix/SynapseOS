### TallyNext

The Tally experience, inside ERPNext.

### Installation

You can install this app using the [bench](https://github.com/frappe/bench) CLI:

```bash
cd $PATH_TO_YOUR_BENCH
bench get-app $URL_OF_THIS_REPO --branch develop
bench install-app tallynext
```

### Contributing

This app uses `pre-commit` for code formatting and linting. Please [install pre-commit](https://pre-commit.com/#installation) and enable it for this repository:

```bash
cd apps/tallynext
pre-commit install
```

Pre-commit is configured to use the following tools for checking and formatting your code:

- ruff
- eslint
- prettier
- pyupgrade
### CI

This app can use GitHub Actions for CI. The following workflows are configured:

- CI: Installs this app and runs unit tests on every push to `develop` branch.
- Linters: Runs [Frappe Semgrep Rules](https://github.com/frappe/semgrep-rules) and [pip-audit](https://pypi.org/project/pip-audit/) on every pull request.

# TallyNext — Architecture

## Design Principle

TallyNext Core is country-agnostic. It knows nothing about GST, TDS, VAT, or any country-specific tax system. Country compliance is delivered via separate installable modules that plug into the **Compliance Plugin API**.

---

## Compliance Plugin API

The interface every country module must implement. Core calls these hooks; the module provides the implementation.

### Registration

A country module registers itself in its `hooks.py`:

```python
# tallynext_india/hooks.py
tn_compliance_module = {
    "name": "India",
    "country": "India",
    "version": "1.0.0",
    "compliance_items": "tallynext_india.compliance.get_due_dates",
    "tax_summary": "tallynext_india.gst.get_tax_summary",
    "filing_status": "tallynext_india.gst.get_filing_status",
    "voucher_validate": "tallynext_india.hooks.voucher_validate",
    "period_close_checklist": "tallynext_india.hooks.get_period_close_checklist",
}
```

### API Contract

| Hook | Called When | Must Return |
|------|-------------|-------------|
| `get_due_dates(company, year)` | Compliance Calendar loads | List of `{name, due_date, frequency, type}` |
| `get_tax_summary(company, period)` | Dashboard loads | `{tax_liability, tax_paid, next_due}` |
| `get_filing_status(company, period)` | Dashboard widget | List of `{return_name, status, due_date}` |
| `voucher_validate(doc, method)` | Any voucher submit | Raise `ValidationError` or return None |
| `get_period_close_checklist(company, period)` | Period lock screen | List of `{task, status, link}` |

### What Core Provides to Modules

- `tn_get_gl_entries(company, from_date, to_date, filters)` — filtered GL with caching
- `tn_get_outstanding(company, party_type, filters)` — AR/AP outstanding
- `tn_register_report(report_name, module)` — adds report to TallyNext reports menu
- `tn_add_compliance_item(company, item)` — adds a due date to Compliance Calendar
- `tn_send_whatsapp(to, template, data)` — uses Core's WhatsApp config

## Core DocTypes

### Voucher Layer

#### `TN Voucher` (virtual wrapper)
- Maps to: `Journal Entry`, `Payment Entry`, `Sales Invoice`, `Purchase Invoice`
- Fields: `voucher_type`, `date`, `narration`, `party`, `ledger_entries` (child)
- Shortcuts: F4 Contra, F5 Payment, F6 Receipt, F7 Journal, F8 Sales, F9 Purchase

#### `TN Voucher Lock`
- Fields: `company`, `from_date`, `to_date`, `locked_by`, `locked_on`
- Enforced via `validate` hooks on all GL-touching DocTypes

### Bank Reconciliation

#### `TN Bank Statement Upload`
- Fields: `bank_account`, `upload_date`, `file`, `status`, `matched_count`, `unmatched_count`
- Parsers: pluggable per bank format (core ships generic CSV; country modules add bank-specific parsers)

#### `TN Bank Reconciliation Line`
- Fields: `date`, `description`, `amount`, `matched_entry`, `match_status`, `match_confidence`

### Compliance Framework

#### `TN Compliance Item`
- Fields: `company`, `compliance_name`, `due_date`, `frequency`, `status`, `reference_no`, `filed_on`, `source_module`
- Populated by: country modules via `tn_add_compliance_item()`; or manually

#### `TN Compliance Alert`
- Fields: `compliance_item`, `alert_type` (Email/WhatsApp), `sent_on`, `status`

### PDC

#### `TN PDC Entry`
- Fields: `type` (Received/Issued), `party`, `bank`, `cheque_no`, `cheque_date`, `amount`, `status`

### Recurring Transactions

#### `TN Recurring Template`
- Fields: `voucher_type`, `ledger_entries`, `schedule_type`, `start_date`, `end_condition`, `auto_submit`

#### `TN Recurring Queue`
- Fields: `template`, `scheduled_date`, `status` (Pending/Confirmed/Skipped), `created_entry`

### Budget

#### `TN Budget`
- Fields: `company`, `fiscal_year`, `status` (Draft/Approved/Active), `approved_by`

#### `TN Budget Detail` (child)
- Fields: `account`, `cost_centre`, `jan` … `dec` (monthly amounts)

### Multi-currency / Multinational

#### `TN Currency Revaluation`
- Month-end unrealised gain/loss on foreign currency balances
- Fields: `company`, `period`, `currency`, `exchange_rate`, `gl_entries` (child)

#### `TN Transfer Pricing Log`
- Inter-company / cross-border transaction documentation
- Fields: `from_company`, `to_company`, `transaction_type`, `amount`, `currency`, `arm_length_price`, `documentation`

### WhatsApp

#### `TN WhatsApp Config`
- Fields: `provider` (WATI/Interakt/Meta), `api_key`, `phone_number_id`, `company`

#### `TN WhatsApp Log`
- Fields: `to`, `template`, `status`, `sent_on`, `document_type`, `document_name`

### Settings

#### `TN Settings` (Single DocType)
- Fields: `default_voucher_type`, `keyboard_shortcut_profile`, `bank_statement_format`, `whatsapp_provider`, `active_compliance_modules`

## Multinational Companies

A company operating in multiple countries (e.g., India + UAE) installs both `tallynext_india` and `tallynext_uae`. Core handles:

- **Multi-currency GL** — leverages ERPNext's existing multi-currency support
- **Per-entity compliance** — each company entity gets its own country module active
- **Consolidated reporting** — consolidation always runs in the group's base currency
- **Transfer pricing log** — cross-border inter-company transactions documented in `TN Transfer Pricing Log`
- **Currency revaluation** — month-end unrealised FX gain/loss via `TN Currency Revaluation`
- **Compliance Calendar** — shows due dates across all entities in one view, tagged by country

A single user can manage Indian subsidiary (GST/TDS) and UAE subsidiary (VAT) from the same TallyNext interface — country modules activate per company, not per user.

# tallynext_india — India Compliance Module

**App:** `tallynext_india`
**Depends on:** `tallynext` (core), `erpnext`, `india_compliance`
**Target:** Indian businesses using ERPNext + TallyNext Core

---

## Key Principle

**We do not reinvent compliance.** The `india_compliance` app (by Resilient Tech) already handles:
- GST returns (GSTR-1, 2B, 3B, 9, 9C)
- E-Invoice (IRN generation via IRP)
- E-Way Bill
- TDS (deduction, challan, Form 26Q, Form 16A)
- HSN / SAC codes
- GSTIN validation

`tallynext_india` is the **UX and reporting layer on top of `india_compliance`**. We surface its data beautifully, connect it to the Compliance Calendar, add dashboard widgets, and fill the gaps it doesn't cover.

```
tallynext_india
    │
    ├── depends on: india_compliance (compliance engine)
    ├── depends on: tallynext (core UX framework)
    └── provides: Better UX, reports, dashboard widgets,
                  compliance calendar integration,
                  features india_compliance doesn't have
```

---

| Feature | Our Role |

## What `tallynext_india` Adds (gaps not covered by india_compliance)

### 1. Compliance Calendar — India Due Dates

`india_compliance` tracks filing status but has no calendar view. We register all India due dates into TallyNext Core's `TN Compliance Item` framework.

**Auto-registered on company setup:**

| Compliance | Due Date | Frequency | Trigger |
|------------|----------|-----------|---------|
| GSTR-1 (turnover > ₹5cr) | 11th | Monthly | GSTIN set |
| GSTR-1 (QRMP scheme) | 13th | Quarterly | GSTIN + QRMP flag |
| GSTR-3B | 20th | Monthly | GSTIN set |
| TDS Deposit | 7th | Monthly | TAN set |
| TDS Return (26Q) | 31st after quarter end | Quarterly | TAN set |
| Advance Tax | 15 Jun / 15 Sep / 15 Dec / 15 Mar | Quarterly | Always |
| Professional Tax | State-specific | Monthly / half-yearly | PT state set |
| PF Deposit | 15th | Monthly | PF number set |
| ESI Deposit | 15th | Monthly | ESI number set |
| ITR Filing | 31st Oct (audit) | Annual | Always |
| ROC (AOC-4) | 30 days after AGM | Annual | Always |

**Filing status sync:** When `india_compliance` marks a return as filed, `tallynext_india` updates the corresponding `TN Compliance Item` to "Filed" automatically (via doctype hooks).

### 4. Advance Tax Module

`india_compliance` does not cover Advance Tax. This is ours.

- Estimate annual profit from YTD P&L + projection
- Compute total tax liability (after TDS credit from 26AS)
- Installment schedule:
  - 15% by 15 June
  - 45% by 15 September
  - 75% by 15 December
  - 100% by 15 March
- Log challan: BSR code, challan no, deposit date, amount
- Running balance: paid vs required vs shortfall
- **Section 234B/C interest calculator** (penal interest on shortfall)
- Auto-registered in Compliance Calendar

**DocTypes:** `TN Advance Tax Challan`

---

### 5. Professional Tax (PT) Module

`india_compliance` covers GST and TDS but not PT. This is ours.

- State-wise PT slabs: Maharashtra, Karnataka, Gujarat, Tamil Nadu, West Bengal
- Auto-calculate PT from Salary Slips
- PT payable tracking per month
- PT challan entry
- PT return report (state-specific format)
- Auto-register PT due dates in Compliance Calendar per active PT state

---

### 6. MSME Payment Compliance

Not in `india_compliance`. This is ours.

- Flag suppliers as MSME (Micro / Small / Medium) with Udyam Registration Number
- Legal limit: 45 days from invoice date
- Alert at Day 30, Day 40, Day 45+ breach
- Interest liability: 3x SBI MCLR on delayed payments
- MSME outstanding report (required for MSME Form 1 — half-yearly filing)
- MSME Form 1 data export
- MSME Form 1 due dates auto-registered in Compliance Calendar

**DocTypes:** `TN MSME Vendor`

---

### 7. Form 26AS / AIS Reconciliation

Not in `india_compliance`. This is ours.

- Upload Form 26AS (TRACES XML) — TDS deducted by payers on company's PAN
- Match against TDS receivable in books (TDS on sales, bank interest)
- Status: Matched / Mismatch / Missing in Books / Missing in 26AS
- Upload AIS JSON (from income tax portal)
- Compare: Sales turnover in AIS vs ERPNext Sales Invoices
- Compare: Interest income, purchase transactions
- Discrepancy report for CA before ITR filing

**DocTypes:** `TN TaxCredit Upload`, `TN TaxCredit Line`

### 9. Period-Close Checklist — India

Plugs into Core's period lock screen. Before locking a month, shows:

- [ ] GSTR-1 filed for this period
- [ ] GSTR-3B filed and payment made
- [ ] TDS deposited (7th deadline passed)
- [ ] Advance Tax current (if quarter-end)
- [ ] Bank reconciliation complete
- [ ] MSME payments within 45 days (no breach)

ERPNext is powerful. Accountants worldwide don't care. They care about:

- Booking 50 vouchers before lunch
- Not panicking at month-end close
- Telling their auditor the books are clean

TallyNext exists to make all three effortless inside ERPNext — regardless of which country the accountant is in.

## What We Are NOT

- Not a Tally clone
- Not a Tally replacement
- Not India-only software
- Not a workaround or hack
- Not just a UI theme

We are the **accounting UX layer** that ERPNext was always missing — built for global deployment, with compliance modules for each market.

```
TallyNext Core              ← works anywhere ERPNext runs
└── tallynext_india         ← India compliance module (GST, TDS, e-way bill)

```

The core product ships with zero country-specific compliance baked in. Country modules install on top and plug into the Compliance Plugin API.

## Design Philosophy

### 1. Keyboard is King
Every workflow must be completable without touching the mouse. If you need the mouse to submit a voucher, we failed.

### 2. Accountant's Vocabulary
We speak the accountant's language — not the ERP developer's:

| ERPNext Says | TallyNext Says |
|-------------|----------------|
| Journal Entry | Voucher |
| Account | Ledger |
| Warehouse | Godown |
| Cost Center | Cost Centre |
| Customer/Supplier | Party |
| Debit Note | Debit Memo |

### 3. Information Density over Beauty
Dense, data-rich screens over card layouts. Accountants read fast. Give them everything on one screen.

### 4. Trust through Immutability
Locked periods. Tamper-proof audit trails. If an accountant locks a month, it stays locked. Period.

### 5. Extensible by Design
Country compliance is a module, not a fork. The core ships clean. A country module adds its DocTypes, hooks into the Compliance Plugin API, and registers its due dates with the Compliance Calendar. The core never needs to know about GST or VAT.

### 6. Print-Ready Always
Every report should look right when printed or exported to PDF/Excel. No extra formatting steps.

# TallyNext — Performance Guide

## The Problem

A company with 3+ years of data on ERPNext can have:
- 500,000+ GL Entries
- 100,000+ vouchers (Journal Entry, Payment Entry, Sales/Purchase Invoice combined)
- 50,000+ parties

Without deliberate performance design, reports that work in 0.5 seconds for a new company will take 45 seconds for this company. That kills adoption.

---

## Performance Targets

| Operation | Target | Acceptable max |
|-----------|--------|----------------|
| Voucher submit |  5 seconds on large data must run as background jobs.

### Reports that need background processing at scale

- GSTR-1 generation (large companies: 10,000+ invoices/month)
- GSTR-9 annual return
- Tally XML Import (always background)
- Bank statement auto-match (always background for > 200 lines)
- Audit pack generation (ZIP of multiple reports)
- Consolidated financial statements (multi-company)

### Pattern

```python
# Enqueue
@frappe.whitelist()
def generate_gstr1(company, period):
    job = frappe.enqueue(
        "tallynext.gst.gstr1.generate",
        company=company,
        period=period,
        queue="long",
        timeout=300,
        job_id=f"gstr1:{company}:{period}"  # prevents duplicate jobs
    )
    return {"job_id": job.id, "status": "queued"}

# Frontend polls /api/method/frappe.utils.background_jobs.get_job_status
# When complete, shows download button
```

---

## Report Pagination

List reports (Ledger Statement, Day Book, Ageing) must paginate for large data.

- Default page size: **500 rows**
- Max page size: **5000 rows** (for Excel export)
- Always show total count first (fast COUNT query)
- Load first page instantly, lazy load on scroll

For Excel exports of > 5000 rows, always use background job + email/notification when ready.

---

## Frappe Page Performance

### Voucher Entry Page

- Ledger autocomplete: debounce 200ms, fetch max 20 results, index on `account_name`
- Amount expression evaluator: run client-side (no server round-trip)
- Submit: single API call, no reload — update day book counter in-place

### Dashboard Page

- All 6 widgets load in parallel (Promise.all)
- Each widget has its own cached endpoint
- If any widget fails, show error in that widget only — don't break the whole dashboard
- Auto-refresh: use `setInterval` with 5-minute TTL, not page reload

### Day Book Page

- Virtualized list — render only visible rows (50 rows at a time)
- Pre-fetch next/previous day in background on idle

---

## Database Archival

For companies with 5+ years of data, consider archival of old GL entries.

### Strategy (do not implement until Phase 4)

- Archive GL entries older than 3 financial years to `tabGL Entry Archive`
- Same schema, same indexes
- All TallyNext reports query both tables with UNION when date range spans archive
- Archived data is read-only
- Archival runs as a yearly background job in April (after year-end close)

---

## Load Testing

Before each major release, run load tests against a seeded large-data instance.

### Test Data Seed

```
Company: 5 years of data
GL Entries: ~750,000
Vouchers: ~150,000
Parties: ~5,000
```

### Benchmark Script

```bash
# Run before release on staging with seeded data
bench execute tallynext.tests.performance.run_benchmarks

# Checks:
# - Trial Balance (12 months): must be  1s:
```ini
slow_query_log = 1
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 1
```

Review weekly. Any new slow query pattern → add index or optimize before next release.

### Frappe Performance Monitor

- Enable `frappe.utils.monitor` in production
- Alert if any TallyNext API endpoint P95 > 3s
- Dashboard: track report generation times over time

---

## Phase-by-Phase Performance Budget

As features are added, these budgets must be maintained:

| Phase | New heavy operations | Strategy |
|-------|---------------------|----------|
| 1 | Trial Balance, Ageing | Raw SQL + indexes |
| 2 | GSTR-1, TDS calcs, bank auto-match | Background jobs + Redis cache |
| 3 | Tally XML import, consolidated statements | Always background, chunked processing |
| 4 | Loan amortization, collection analysis | Pre-computed on save, not on report |

## Core Features (country-agnostic)

### 1. Smart Bank Reconciliation

The feature ERPNext gets the most complaints about. Bank reconciliation must be as smooth as Tally's — for any bank, in any country.

#### Bank Statement Upload

- Support formats: CSV, Excel, OFX, PDF (with OCR fallback)
- Generic CSV parser ships in core
- Country modules register bank-specific parsers (e.g., tallynext_india registers HDFC, ICICI, SBI, Axis, Kotak)
- Auto-detect format from header row
- Parsed preview before confirming upload

#### AI Auto-Matching

- Match bank statement lines to ERPNext Payment Entries / Journal Entries by:
  - Amount (exact match first)
  - Date proximity (±3 days)
  - Party name similarity (fuzzy)
  - Narration keyword match
- Confidence score per match: High / Medium / Low
- Auto-accept High confidence matches
- Queue Medium/Low for human review

#### Reconciliation UI

- Two-panel view: Bank Statement (left) | ERPNext Entries (right)
- Matched pairs in green, unmatched in amber
- Click to manually link any statement line to any ERPNext entry
- Split one statement line to multiple ERPNext entries
- Create missing entries directly from reconciliation screen

#### Bank Reconciliation Statement

- Standard format: Opening balance → Deposits → Withdrawals → Closing balance
- Variance section: In bank not in books / In books not in bank
- Print-ready, date-parameterised, works in any currency

**DocTypes:** `TN Bank Statement Upload`, `TN Bank Reconciliation Line`

- Every voucher: created_by, created_on, last_modified_by, last_modified_on

### 1. Tally XML Import

The single biggest barrier to ERPNext adoption is "But all my historical data is in Tally." This removes it.

#### What Gets Imported

| Tally Data | ERPNext Target |
|------------|----------------|
| Masters: Ledgers | Chart of Accounts |
| Masters: Groups | Account Groups |
| Masters: Cost Centres | Cost Centers |
| Masters: Godowns | Warehouses |
| Masters: Stock Items | Items |
| Masters: Units | UOM |
| Vouchers: Payment | Payment Entry |
| Vouchers: Receipt | Payment Entry |
| Vouchers: Journal | Journal Entry |
| Vouchers: Contra | Journal Entry |
| Vouchers: Sales | Sales Invoice |
| Vouchers: Purchase | Purchase Invoice |
| Vouchers: Debit/Credit Note | Return Invoice |
| Opening Balances | Opening Entry |

#### Import Process

**Step 1: Upload Tally XML**
- Accept Tally's Data Export XML (exportable from any Tally version)
- Parse and validate structure
- Show summary: N ledgers, N vouchers, date range

**Step 2: Ledger Mapping**
- Auto-suggest ERPNext account for each Tally ledger (by name similarity + group)
- Manual override for each mapping
- Map to existing accounts or create new
- Save mapping for future imports (same company → same mapping)

**Step 3: Validation Report**
- Run before actual import
- Flag: Unmapped ledgers, Missing parties, Duplicate voucher numbers, Balance mismatches
- Must show zero errors before final import is allowed

**Step 4: Import**
- Background job (large imports can have 100k+ vouchers)
- Progress bar with real-time count
- Rollback on failure (all-or-nothing per batch)
- Import log with success/failure per voucher

**Step 5: Reconciliation**
- After import: Compare opening + all vouchers = closing balance
- Match Tally trial balance vs ERPNext trial balance
- Any difference flagged with drill-down

**DocTypes:**
- `TN Tally Import Job` — tracks import status
- `TN Ledger Mapping` — Tally ledger → ERPNext account mapping (reusable)
- `TN Import Log` — per-voucher import result

### 3. Advance Tax Module

### 4. MSME Payment Compliance

Legally mandatory under MSME Development Act. Penalty: 3x bank rate interest on delayed payments. Most companies ignore this until they get a notice.

#### MSME Vendor Registry

- Flag each supplier as MSME (Micro / Small / Medium) with Udyam Registration Number
- Import from Udyam portal (via registration number lookup — API)
- Store: registration date, category, validity

#### Payment Due Date Tracking

- For MSME vendors: payment due = invoice date + 45 days (max, regardless of credit terms)
- Alert at 30 days (15 days to go)
- Alert at 40 days (5 days to go)
- Alert at 45 days if unpaid: **Legal limit breached**

#### MSME Outstanding Report

- All unpaid MSME invoices with:
  - Days outstanding
  - Days past 45-day limit
  - Accrued interest liability (3x bank rate)
- Required for MSME Form 1 filing (half-yearly)

#### MSME Form 1 Assistance

- Auto-populate outstanding amounts as of April 30 and October 31
- Export in required format
- Due dates in compliance calendar

### 5. Loan & EMI Tracker

#### Loan Register

- Amortization schedule auto-calculated on creation (standard reducing balance)
- Stores complete schedule: month-wise EMI, principal portion, interest portion, closing balance

#### Monthly EMI Booking

- On EMI due date, appears in Recurring Queue (integrates with Phase 2 recurring system)
- One-click booking: auto-splits into principal (reduces loan liability) and interest (expense)
- TDS on interest auto-applied where applicable (Section 194A)
- EMI paid vs scheduled comparison

#### Prepayment Handling

- Part-prepayment: reduces outstanding, recalculates remaining schedule
- Full closure: closes loan account, records any foreclosure charges
- Print closure certificate

#### Reports

- Loan outstanding report (all loans, principal remaining, interest paid YTD)
- Bank-wise borrowing summary
- Interest expense summary (monthly, YTD) — matches P&L interest line
- Loan maturity calendar (which loans end when)

# TallyNext — Master Plan

> "ERPNext accounting that accountants actually love."

## The Problem

Accountants worldwide live in two worlds — their trusted accounting tool (Tally, Sage, QuickBooks) and ERPNext. The gap between them causes manual re-entry, errors, delays, and frustrated finance teams who resist ERPNext adoption.

Tally wins on speed, familiarity, and compliance. ERPNext wins on operations, inventory, HR, and collaboration. Neither side wants to give up their advantage.

TallyNext closes that gap — everywhere ERPNext runs.

## The Solution

TallyNext is a Frappe app that wraps ERPNext's accounting engine in a speed-first, accountant-native experience. Not a Tally clone. Not a replacement. A layer — making ERPNext feel native to the accountant's brain.

**Country compliance is modular.** The core product works anywhere. Country-specific compliance (GST, TDS, VAT, MTD) installs as a separate module via the Compliance Plugin API.

# TallyNext — Testing Strategy

## Why This Document Exists

Accounting software bugs are not like regular software bugs. A wrong calculation in the voucher entry or a rounding error in GST computation corrupts financial books. Restoring trust after a accounting data corruption incident is nearly impossible. This strategy is non-negotiable.

**Rule:** No feature ships without tests that would have caught the most likely failure modes.

---

## Test Layers

```
                    ┌─────────────────────┐
                    │   E2E Tests         │  ← Playwright, full user flows
                    ├─────────────────────┤
                    │   Integration Tests │  ← Real ERPNext + MariaDB
                    ├─────────────────────┤
                    │   Unit Tests        │  ← Python logic, pure functions
                    └─────────────────────┘
```

---

## Layer 1: Unit Tests (Python)

**Framework:** Python `unittest` + Frappe's test runner (`bench run-tests`)
**Location:** `tallynext/tests/unit/`
**Run on:** Every commit (pre-commit hook + CI)

### What gets unit tested

#### Calculation Logic (highest priority)
These must be 100% covered — they involve money.

- GST tax calculation (IGST vs CGST+SGST split by state)
- TDS rate lookup (section + PAN status + lower cert)
- TDS amount calculation with threshold check
- Advance tax installment amounts (15%/45%/75%/100%)
- Section 234B/C interest calculation
- Loan amortization schedule (EMI, principal, interest per month)
- PDC days-to-deposit calculation
- Budget variance percentage
- Ageing bucket assignment (30/60/90/120+ days)
- ITC Rule 42 proportionate reversal formula
- Amount-in-words (Indian number system: lakh, crore)

#### Data Parsing
- Tally XML parser: valid XML, malformed XML, missing fields
- Bank statement CSV parser: each bank format (HDFC, ICICI, SBI, Axis, Kotak)
- GSTR-2B JSON parser: valid structure, missing fields, large file
- 26AS XML parser
- AIS JSON parser

#### Validation Logic
- GSTIN format validation (15-char, state code, checksum)
- PAN format validation
- IFSC code format
- Cheque number uniqueness check
- Period lock enforcement (is date in locked period?)

### Example unit test structure

```python
# tallynext/tests/unit/test_gst_calculation.py

class TestGSTCalculation(unittest.TestCase):

    def test_intrastate_splits_cgst_sgst(self):
        result = compute_gst(taxable=10000, rate=18, from_state="MH", to_state="MH")
        self.assertEqual(result["cgst"], 900)
        self.assertEqual(result["sgst"], 900)
        self.assertEqual(result["igst"], 0)

    def test_interstate_uses_igst(self):
        result = compute_gst(taxable=10000, rate=18, from_state="MH", to_state="KA")
        self.assertEqual(result["igst"], 1800)
        self.assertEqual(result["cgst"], 0)

    def test_zero_rated_export(self):
        result = compute_gst(taxable=10000, rate=0, export=True)
        self.assertEqual(result["igst"], 0)
        self.assertEqual(result["is_zero_rated"], True)
```

## Layer 2: Integration Tests

**Framework:** Frappe's test runner against a real ERPNext test instance
**Location:** `tallynext/tests/integration/`
**Run on:** Pull request CI, nightly

### Setup

```bash
# CI spins up a fresh Frappe + ERPNext instance
bench new-site test.localhost --install-app erpnext --install-app tallynext
bench run-tests --app tallynext
```

### What gets integration tested

#### Voucher Entry → GL Entry
For each voucher type (F4–F9):
1. Submit voucher via TallyNext API
2. Assert: GL Entry created with correct debit/credit accounts
3. Assert: Debit total = Credit total (books must balance)
4. Assert: Voucher locked after period lock applied

#### GST Compliance Flow
1. Create Sales Invoice with GST
2. Run GSTR-1 for period
3. Assert: Invoice appears in correct section (B2B/B2C/etc.)
4. Export JSON, validate against GSTN schema

#### TDS Flow
1. Create Purchase Invoice with TDS section 194C
2. Assert: TDS Entry created with correct amount
3. Create TDS Challan for the month
4. Generate Form 26Q
5. Assert: FVU file structure is valid

#### Bank Reconciliation
1. Upload test bank statement (fixture file per bank)
2. Run auto-matching
3. Assert: Known-match entries get High confidence
4. Assert: Matched entries reconcile correctly

#### Period Lock
1. Lock period for last month
2. Attempt to create Journal Entry in locked period
3. Assert: Frappe ValidationError raised
4. Attempt with override permission
5. Assert: Entry allowed

#### Tally XML Import
1. Upload sample Tally XML (fixture: 100 vouchers, 20 ledgers)
2. Run import
3. Assert: Trial Balance matches expected values from fixture
4. Assert: No unbalanced entries

#### Recurring Transactions
1. Create recurring template (monthly, start date = yesterday)
2. Run scheduler
3. Assert: Entry appears in pending queue
4. Confirm entry
5. Assert: GL Entry created, next due date advanced

## Known Risk Areas

These are areas where bugs are most likely and tests must be especially thorough:

| Area | Risk | Mitigation |
|------|------|-----------|
| GST state code mapping | Wrong CGST/SGST vs IGST split | Test all 36 state/UT combinations |
| TDS threshold tracking | Annual threshold missed across multiple invoices | Cumulative amount test per vendor per year |
| Tally XML parsing | Encoding issues (Tally uses non-UTF-8 in older versions) | Test with CP1252 encoded files |
| Period lock bypass | Custom DocType methods not hooked | Enumerate all GL-touching DocTypes, verify hook on each |
| Rounding | GST amounts in GSTR-3B vs books differ by ₹1 | Round at same precision, same point in code |
| Recurring transaction timing | Scheduler fires twice on DST change day | Idempotency check before creating entry |
